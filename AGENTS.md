# ocache

Composable caching primitives. works with any runtime that has standard `Request`/`Response`.

## Project Structure

```
src/
├── index.ts        # Public exports (re-exports from all modules)
├── types.ts        # All type definitions (HTTPEvent, CacheEntry, CacheOptions, etc.)
├── cache.ts        # Core: defineCachedFunction, cachedFunction, invalidateCache, resolveCacheKeys
├── http/           # HTTP layer: defineCachedHandler (depends on cache.ts)
│   ├── index.ts         # defineCachedHandler: the wiring onto cachedFunction + the serve path
│   ├── config.ts        # Caller options -> the per-handler `HandlerConfig` every module reads
│   ├── request.ts       # What bypasses the cache + narrowing what the handler may see
│   ├── key.ts           # Cache key: resource identity + method component
│   ├── filters.ts       # Cookie/query allowlist filters, shared by request.ts and key.ts
│   ├── entry.ts         # Storage codec both ways: Response <-> ResponseCacheEntry
│   ├── validate.ts      # The `validate` hook: status allowlist + response-side opt-outs
│   ├── cache-control.ts # RFC 9111 directive parser (no policy, just syntax)
│   ├── vary.ts          # Vary merging and the two response-`Vary` predicates
│   └── conditional.ts   # 304 decisions and the headers a 304 must echo
└── storage.ts      # Storage interface + built-in memory storage
```

### Core caching (`cache.ts`)

- `defineCachedFunction(fn, opts)` — wraps any function with caching (SWR, TTL, integrity checks, deduplication of in-flight requests)
- Cache key `name` resolves as `opts.name || fn.name || \`anon_<hash(fn)>\``— in`resolveName`, an internal exported from `cache.ts`and **shared with`http/config.ts`** (which passes the wrapped `EventHandler`as`fn`) so the two paths cannot drift; both call it on the caller's options *before* the `defaultCacheOptions()`merge, which is the whole point (see the HTTP section's `name` bullet). Resolved once and written back into`opts`so the internal read/write path and the`resolveKeys`/`invalidate`/`expire` helpers all agree. Named/`fn.name`functions get a stable, human-readable name; anonymous functions fall back to a source hash so distinct inline fns don't collide (they would otherwise share one key and thrash). Caveat: a source hash can't tell apart same-source fns that differ only by closed-over variables — pass an explicit`name`(or`getKey`) for those. When reconstructing keys via the standalone `resolveCacheKeys`/`invalidateCache`/`expireCache`helpers (which can't see`fn`), always pass the same `name` you cached with
- `getMaxAge(entry)` option — dynamic per-entry TTL: runs after the resolver, returns a number (seconds, shorthand for `maxAge`) or `{ maxAge?, staleMaxAge? }` that override the static options for that entry. Resolved values are persisted on the entry (`CacheEntry.maxAge` / `CacheEntry.staleMaxAge`) and drive the read freshness check, the storage TTL and — in `defineCachedHandler` — the synthesized `Cache-Control` (finding 10.2), so the lifetime advertised downstream is the one enforced here. Absent field / `undefined` → falls back to static options. Flows through to `defineCachedHandler`, where it runs before the internal `serialize` hook so `entry.value` is the live `Response` (inspect its headers/status; don't consume its body — `serialize` reads it exactly once). `http/index.ts` always installs its own wrapper around the caller's hook (for `must-revalidate` — see the HTTP section), so a handler's entry always carries resolved `maxAge`/`staleMaxAge` fields, `undefined` when neither the caller nor the wrapper set one
- `serialize(entry, { args })` option — write-side counterpart of `transform`: runs once right after the resolver (and after `getMaxAge`, so that hook still sees the raw value) and returns the value to persist. `transform` deserializes it back on read. Use for resolver outputs a storage backend can't persist as-is (raw `ReadableStream`, class instances). It runs **exactly once per resolution** — shared across concurrent, deduplicated calls (every caller observes the serialized value), so consuming a one-shot source like a stream is safe. A throwing `serialize` fails the call and evicts, like a rejected resolver. Both `getMaxAge` and `serialize` are folded into the shared in-flight (`pending`) promise so they never run more than once
- The in-flight dedup registry (`pending`) is a **`Map`, never a plain object**: keys are caller-controlled (the documented `getKey: (id) => id`), and a plain object inherits from `Object.prototype`, so `pending["constructor"]` / `"toString"` / `"valueOf"` / `"hasOwnProperty"` / `"__proto__"` / `"isPrototypeOf"` / `"propertyIsEnumerable"` / `"toLocaleString"` read truthy with nothing in flight. Such a call was treated as a deduplicated follower, `await`ed the inherited member (not a thenable, so it resolved to itself), never called the resolver, and cached `undefined` — silently for `defineCachedFunction`, and as a hard, permanent `TypeError` for `defineCachedHandler` (whose `transform` then dereferences `undefined.headers`). Default keys can't hit it (the auto handler key always contains a `.`; `cache.ts`'s default is `hash(args)` or `""`), so it takes a custom `getKey`. Unrelated to prototype _pollution_ — there is none; this was unsafe prototype-chain _reading_
- **`resolverTimeout` (ms, default `30_000`)** — a deadline on one shared in-flight resolution, i.e. on the resolver _plus_ the `getMaxAge` and `serialize` hooks folded into the same `pending` promise (`withDeadline`; `Infinity`/`0`/negative disable it, the `createMemoryStorage` normalization shape). A resolution that **never settles** was the one leak in an otherwise clean `pending` lifecycle — the auditor verified cleanup on the resolve path, the reject path, a throwing `getMaxAge`, a throwing `serialize` and a throwing `validate`, and re-verified here — so one hung upstream kept its slot occupied forever and **every later request for that key became a follower of a resolution that would never finish**: the key was dead for the whole process, unrecoverable without a restart (finding 03, part 2; measured `req1`/`req2` both unsettled after 10 s). On the deadline **the waiters reject** (`TimeoutError`, the name `AbortSignal.timeout()` uses), rather than the finding's weaker "at minimum evict the `pending` entry": a caller left awaiting a resolution nobody will complete is not "served" — it holds its request open until something outside kills it, which on a serverless runtime is nothing — and the weaker form fails the finding's own regression test, whose second request is already a follower by the time the deadline fires. Rejecting also means an abandoned resolver that settles **late cannot write**: the whole storage-write block sits after that `await`, so its long-dead value can never land on a key a fresh leader has since re-resolved. It is _not_ cancelled (there is no `AbortSignal` to hand the caller's `fn`) — it keeps running, and `withDeadline` keeps its handlers attached so a late rejection is absorbed rather than surfacing as an unhandled one. The timer is `unref()`ed and cleared on **every** settle path, resolve and reject alike (`.then(f, f)`, never `.finally`, whose returned promise would reject with nothing listening). A timed-out resolution is a **failed** one in every respect, the storage eviction included: "the resolution failed" has exactly one meaning in this file, and a softer one for timeouts would pre-empt the open 19.3 question of whether evicting on failure is right at all, in one arm only. Errors route through the existing shapes — thrown to the caller in the foreground, reported via `onError`/`console.error("[cache] SWR handler error.")` for a background refresh, which is the same wedge and is covered by the same deadline. Deliberately **not** in `defaultCacheOptions()`/`defaultHandlerOptions()`, so the default doesn't materialize as a key on `opts` and cool every existing entry; setting it explicitly does cost that one integrity change, since it stays in `integrityOpts` (it is not a storage-_location_ field, and carving out the first exception to that rule to spare one cold read is the wrong trade). Flows to `defineCachedHandler` for free — `http/index.ts` spreads the caller's options into `_opts`. Two consequences worth stating: a slow-but-eventually-fine upstream that would have answered at 31 s now **fails** at 30 s (raise or disable the option — that is the trade the strong form buys), and the extra promise between a resolution and the leader's write means a **sync** resolver's SWR background refresh no longer lands on `entry.value` before the serve path returns, so `swr` now serves the stale value for sync and async resolvers alike. The latter was always a microtask-tick accident (an async resolver never made it in time); it is asserted in `test/index.test.ts`. Uncovered by design: storage `get`/`set` are outside the shared promise, so a wedged backend is a different problem
- **Lifetimes and the storage TTL** — `storageTtl(maxAge, staleMaxAge, swr)` is the single decision point, returning `{ ttl }`, `undefined` ("store it, no TTL") or `false` ("don't store it"). `remainingTtl` (the `expireCache` rewrite) derives from the same call, so expiring an entry can neither extend its life, nor strip a TTL off it, nor arm one the write withheld — it duplicated the logic before, which is exactly how the three could drift. The TTL covers the window an entry may still be served in: `maxAge + staleMaxAge` under SWR, `maxAge` without it, and **no TTL under SWR with no `staleMaxAge`** (a negative one states no window and reads as unset). The rule is **never write an entry that has neither an expiry nor a storage TTL** (finding 10.6) — and the two shapes it has to tell apart are genuinely different, so the code comment spells the distinction out rather than leaving it to be "fixed" again:
  - `{ swr: true, maxAge: 60 }` — **has** an expiry (`entry.expires` from `maxAge`), no TTL. Merely _retained_ past the moment it goes stale, which is the whole of ISR: the last good value keeps being served while a background refresh replaces it, and a _failed_ refresh keeps serving the last success (Next.js's `revalidate` marks a page eligible for regeneration, it never deletes it; Vercel bounds ISR by storage capacity, never by a timer — and `x-nextjs-cache`'s `HIT`/`STALE`/`MISS` is the vocabulary `x-cache` deliberately mirrors). **Allowed.** Finding 14.3 proposed defaulting this TTL to `maxAge`; it is **rejected** (`[-]` in the tracker) because the entry would then be deleted the instant it went stale, degrading SWR to foreground revalidation and making the documented ISR recipe (`docs/1.guide/9.isr.md`) impossible. The bound on this shape is the storage backend's **capacity** — not a timer — and since finding **14.1** the built-in backend actually is one: `createMemoryStorage` evicts above **10 000 entries or 100 MB** (`maxSize` / `maxBytes`, LRU, both applied). An external backend still needs its own capacity bound, which the recipe documents
  - `{ maxAge: 0 }`, or a `getMaxAge` clamped to it — **neither** an expiry nor a TTL: unservable-as-fresh _and_ unreclaimable, a permanent HIT. **Refused**, and a prior entry on that key is evicted instead (which also clears what an older ocache left). The read path treats such an entry as expired on arrival, so it could only ever be purged by hand. A **nullish** `maxAge` is refused with it, but is no longer reachable through either defaults merge (both supply `maxAge: 1`, which an explicit `undefined` no longer defeats — see the next bullet); it stays live for the standalone `expireCache`, which merges no defaults
- **An option explicitly set to `undefined` is treated as unset** (`definedOptions`, exported from `cache.ts` and applied to the caller's options at _both_ defaults merges — `defineCachedFunction` and `http/config.ts`'s `resolveHandlerConfig` — the shared-internal pattern of `resolveName`/`resolveStorage`). Object spread copies own properties _including_ undefined-valued ones, so `{ ...defaults(), ...opts }` let `{ maxAge: undefined }` clobber the `maxAge: 1` default while `{}` kept it: measured, `{}` resolved once and wrote `{ ttl: 1 }` while `{ maxAge: undefined }` resolved on every call and wrote nothing. That spelling is what plumbing produces, never what anyone types — `defineCachedHandler(h, { maxAge: routeConfig.maxAge })` with an unset rule — and the route then silently stopped caching, no error, no warning. Predates finding 10.6 (before it, the same divergence cached _forever_ instead) and applies to **every** option, not just the lifetimes: `swr`/`staleMaxAge`/`storage`/`getKey`/`varies` all had the shape. Only `undefined` is dropped — `null` is left as written, and stays a nullish (refused) lifetime. Applied to a **copy**: the caller's own object must stay untouched, since it is the storage memo slot, and `resolveName`/`resolveStorage` still read the original. Costs an integrity change for exactly the options objects that carry an undefined-valued key (ohash walks one), i.e. one cold read per affected entry; an object without them hashes byte-identically. Idempotent, which is what makes the handler path safe — it merges twice (`resolveHandlerConfig`, then `cachedFunction` over `_opts`), and the second pass sees only an already-cleaned object plus `http/index.ts`'s own hooks. **Subsumes** the earlier `swr`-without-`maxAge` normalization (`resolveMaxAge`, removed): "no `maxAge`" is not a configuration any merge can produce, since the default supplies `1` and an explicit `undefined` now reads as absent — the only remaining zero-lifetime spellings are an explicit `<= 0` and a `getMaxAge` that yields one, both already refused above. `{ swr: true, staleMaxAge: 600 }` therefore caches for the default second (with the ISR retention that `swr` implies), which is what `{}` has always done, rather than not caching at all
- `cachedFunction(fn, opts)` — alias for `defineCachedFunction`
- Returned cached function has `.resolveKeys(...args)`, `.invalidate(...args)`, and `.expire(...args)` methods
- `resolveCacheKeys({ options, args })` — standalone helper to resolve storage keys
- `invalidateCache({ options, args })` — standalone helper to remove cached entries across all base prefixes
- The standalone helpers are generic over `args` and know nothing about HTTP methods, so for a `defineCachedHandler` key they only ever cover the **one method variant** their `args` imply (same class of caveat as needing the same `name`). Use the handler's own `.invalidate(event)` / `.expire(event)` to cover every variant of a resource
- `expireCache({ options, args })` — standalone helper to mark entries stale (`CacheEntry.stale`) without removing them: SWR keeps serving stale within the original `staleMaxAge` window while the next access triggers a background refresh
- Storage is **per instance**: `opts.storage` (a `StorageInterface` or a factory returning one), defaulting to a fresh `createMemoryStorage()` for each cached function/handler. Resolved lazily via `resolveStorage(_optsRef, opts)` on the first read/write (never at definition time — factories exist for late binding) and memoized back into the caller's own options object _and_ the internal clone, so a factory runs at most once and the `.invalidate()`/`.expire()` methods and the standalone helpers all reach the same store. The standalone `invalidateCache`/`expireCache` helpers reach that store only when handed the **same options object** (or an explicit `storage`), so they **throw** on an unset `storage` (`requireStorage`) rather than purging a fresh empty store while the stale entry keeps being served. A mismatched `name`/`getKey` still no-ops silently — that caveat is unchanged and exactly like `name`'s. `resolveCacheKeys` is pure key derivation, never touches storage, and is unaffected
- Supports `waitUntil` on `event.req` (srvx/Cloudflare ServerRequest pattern) for background cache writes

### HTTP handler caching (`http/`)

Split across the modules listed under Project Structure. The bullets below are about the handler as a whole; each mechanism lives in the module its name suggests — the derived cookie/header/query lists (`HandlerConfig`) in `config.ts`, the composed bypass (`resolveBypass`) + request narrowing in `request.ts`, `resolveKey`/`methodKey`/`cacheableMethods` in `key.ts`, the `filterCookie`/`filteredSearch` allowlists those two share in `filters.ts`, the internal `serialize` hook **and its read-side mirror** `deserializeEntry` (plus the base64 codec, the transport-header strip and the null-body statuses, all private) in `entry.ts`, the `validate` hook + the status allowlist in `validate.ts`, the `Cache-Control` directive parser those decisions read in `cache-control.ts`, `Vary` mechanics in `vary.ts`, and the 304 exchange in `conditional.ts`. `index.ts` holds only the wiring: the `CacheOptions` hooks handed to `cachedFunction`, the resolver, the serve path and the revalidation helpers. Two modules are named for the `CacheOptions` hook they implement (`entry.ts`'s `serialize`, `validate.ts`), and the dependency graph is a DAG — `cache-control.ts`, `vary.ts`, `conditional.ts` and `config.ts` import nothing from the directory.

- `defineCachedHandler<E extends HTTPEvent>(handler, opts)` — wraps an `EventHandler` with response caching (generic over event type)
- Cache key `name`: resolved with `cache.ts`'s shared `resolveName(opts.name, handler)` **before** the `defaultHandlerOptions()` merge (`config.ts`'s own defaults — deliberately not `cache.ts`'s `defaultCacheOptions()`, since only the HTTP layer has a `cacheStatusHeader`, and named apart so neither can be imported for the other), exactly like `defineCachedFunction`. Merging first (the old order) left `opts.name` permanently `"_"` by the time `cachedFunction` re-derived it, so issue #53's fix never reached the HTTP layer and **every** handler keyed as `name: "_"`. Two handlers sharing one `storage` (the configuration `types.ts` recommends) that can see the same path then collided: identical source ⇒ identical integrity ⇒ one served the other's cached response (cross-handler leak); differing source ⇒ every read failed the other's integrity check ⇒ permanent thrash at 0% hit rate. **Breaking key change**, not a behavior change: every existing handler entry goes cold once (the key gains a real name segment). The `HEAD:` method component still sits directly after the name segment, so key shape is otherwise unchanged. Same **documented caveat** as `defineCachedFunction`, and it bites harder here because the shared-`storage` setup turns it into a leak: `hash(handler)` sees only source, so handlers from one factory (`(tenant) => defineCachedHandler(() => render(tenant), { storage })`) share a name _and_ an integrity — pass an explicit `name` per instance. A per-instance discriminator (counter/WeakMap/randomness) is inadmissible: keys must be deterministic across process restarts for persistent/shared backends, which is exactly why a source hash is the right fallback
- Split along the `serialize` seam (built on `cache.ts`'s `cachedFunction<Response>`): the **resolver** narrows the request and returns the handler's live `Response`; the internal **`serialize`** hook consumes the body (`res.arrayBuffer()`), synthesizes `etag`/`last-modified`/`cache-control`/`Vary`, strips every `Set-Cookie`, and builds the stored `ResponseCacheEntry`; **`transform`** reconstructs the servable shape and injects the cache-status header on read. `serialize`/`validate`/`transform` are `Omit`ted from the user-facing `CachedEventHandlerOptions` so internal use doesn't collide
- Binary responses: `serialize` reads the body as bytes and decides by **byte validity, not content-type** — a valid-UTF-8 body (fatal `TextDecoder` with `ignoreBOM`, lossless roundtrip) is stored verbatim as a string (unchanged text behavior, stable text etags); anything else (images, protobuf/MVT tiles, arbitrary binary) is base64-encoded and flagged `base64: true` on the `ResponseCacheEntry`. Base64 (not a raw `Uint8Array`) so binary bodies survive JSON-serializing storage backends. On read, a `base64` entry is decoded back to a `Uint8Array` before `createResponse`, so the exact bytes replay untouched. `createResponse` therefore receives `string | Uint8Array | null` (widened from `string | null`)
- Cache key = **resource identity + method component**. `resolveKey` derives the method-free resource part (auto: URL **origin** + path + `varies` header values + allowlisted cookies; or the caller's `getKey`), then `methodKey` prefixes it: **GET is the implicit default and carries no component**, every other cacheable method contributes `<METHOD>:` — today exactly `HEAD:` (`cacheableMethods`, the enumerable counterpart of `shouldBypassCache`'s **method** half — that predicate also bypasses `Range` requests, which is a request property, not a key space; making another method cacheable is a one-line addition to the list, not a key redesign). Closes the h3#1524 audit finding #3 poisoning: GET and HEAD used to share one entry, and a spec-compliant host `toResponse` (h3's, and every real framework's) nulls the body of a HEAD response — exactly the `Response` `serialize` stores — so one anonymous `HEAD /page` seeded the shared entry with a zero-byte body, a synthesized `max-age=N` and a weak etag over that empty body, and every GET for the rest of the TTL got a blank 200 that CDNs/browsers cached and successfully revalidated. Applied around **both** key branches (a custom `getKey` expresses content identity; preventing the method collision is ocache's job either way). Deliberate scoping: GET keys are byte-identical to pre-fix ones so existing entries stay warm, and the cost is one origin dispatch per method per resource per TTL. Non-cacheable methods never reach `getKey`
- The auto key's hashed component covers the **request authority** (scheme + host + port), not just path + search: `_hashedPath = ${_pathname}.${hash([authority(_url), _path])}`. Without it one handler instance serving several hostnames — the normal nitro/h3 vhost deployment — stored **one entry per path across all hosts**, so tenant A's rendering was served to tenant B (h3#1524 finding #2's cross-app body leak, reopened between hosts on one instance after per-instance storage closed it between processes), and an attacker-supplied `Host` that reached a rendered absolute URL (canonical link, `<script src>`, `Location`, a password-reset link) was stored under the shared key and published with the synthesized `s-maxage`/`stale-while-revalidate` and no `Vary` for shared CDNs to propagate. The pre-existing mitigation, `varies: ["host"]`, was off by default and _silently_ a no-op on adapters that don't put `Host` in `req.headers` (a bare `new Request(absoluteUrl)` has none). Derived from `event.url` — what the adapter resolved — **never** from the `Host` header; on adapters that build `url` from that header the two coincide, so a reverse proxy must still normalize it. Goes in the hashed component, never the human-readable `_pathname` prefix (which exists for debuggability only), and is hashed as a **tuple** with `_path` so the origin/path boundary can't be read two ways (an opaque-scheme pathname need not start with `/`). Both `resolveKey` paths get it, since `event.url ?? new URL(event.req.url)` is resolved once. `allowQuery` still narrows the search component exactly as before, and a custom `getKey` is untouched (it expresses content identity — the caller owns the origin there). **Breaking key change, not a behavior change**: GET keys move once, so every existing entry goes cold
- `authority(url)` — `url.origin` when it exists, else `${url.protocol}//${url.host}`. `origin` is preferred because it canonicalizes (lowercased host, default port dropped — `http://h:80` and `http://h` stay one entry), but it is the literal string `"null"` for every **opaque** origin, and that includes any non-special scheme, where a real authority is present and simply not exposed (`new URL("x-proxy://a.example/p").origin === "null"`, as does `b.example`). Using `origin` alone would collapse those onto one `"null"` bucket — recreating exactly the cross-authority collision the component exists to prevent. Authority-less schemes (`file:`/`data:`/`about:`) land on a per-scheme constant, which is right: their identity is entirely in the path, already hashed alongside
- Handles `304 Not Modified` via `if-none-match`/`if-modified-since`
- Sets `cache-control`, `etag`, `last-modified` headers — but never clobbers an explicit `cache-control` set by the handler (SWR/`s-maxage`/`max-age` directives are only synthesized when the handler didn't set one)
- `cache-control` synthesis is gated on `isCacheableStatus`, `hasVaryWildcard` **and** `hasUnkeyedVary` — the same three predicates `validate` rejects on, deliberately shared functions so the advertisement and the storage decision cannot drift (they had: `serialize` runs before `validate` and used to ship the header regardless of the verdict, so a 500 was _not_ stored — origin takes every request, zero protection — while being advertised `s-maxage=60, stale-while-revalidate=600`, pinned at every CDN for 11 minutes and revalidating successfully. Inverted on both sides). Not "synthesize if `validate` passes": the gate covers exactly the rejections a **fresh** response can trip while carrying no `Cache-Control` of its own. `validate`'s remaining rejections split three ways — structurally impossible here (an explicit `no-store`/`private`/`no-cache`/zero-lifetime `Cache-Control` already suppresses synthesis via the `has("cache-control")` check, since it is the handler's own header and we never clobber one; a `set-cookie` is deleted before this point, that `validate` arm being defense-in-depth for foreign entries; a missing body can't occur on a value `serialize` just built) — and **deliberately ungated**: `shouldCache`, a caller's own storage policy, where "ocache doesn't store this, but a CDN may" is a real configuration and `sendCacheControl: false` is the inverse knob. That is the one arm where advertisement and storage may disagree, by the caller's explicit choice. **Both `Vary` verdicts were the gap**, for one reason: unlike every other opt-out they are spelled in a header that leaves `cache-control` empty, so synthesis fired for a response that was never stored (the finding-10.1 shape, one header over) — `Vary: *` first (finding 08), then `hasUnkeyedVary` (finding 13), which a handler declaring `Vary: Accept-Language` trips while setting no `Cache-Control` at all. The gate reads the handler's raw `Vary` (it runs before `appendVary` merges our names in), `validate` reads the merged one; same verdict, since the merge only adds keyed names. Independent of `sendCacheControl: false`, which suppresses synthesis for every status
- **The advertised lifetime is the entry's, not the option's** (finding 10.2): `serialize` is handed the whole `CacheEntry`, not just its `Response`, and reads `entry.maxAge ?? opts.maxAge` / `entry.staleMaxAge ?? opts.staleMaxAge` — the same per-field precedence `cache.ts` applies to the freshness check, the storage TTL and `expireCache`'s rewrite. Reading the static options alone meant `{ maxAge: 3600, getMaxAge: () => 2 }` expired ocache's own entry after 2 s while every shared cache kept that 2-second-old copy for an hour: the dynamic TTL honored at the layer holding the value and discarded at the layer holding the audience, which is most of the hook's purpose. Sound because `http/index.ts` **always** installs its `getMaxAge` wrapper (see the `must-revalidate` bullet), so `cache.ts` always writes both fields onto the entry `serialize` receives — `undefined` there means "no override", never "not asked", and falls back to the static option, per field. The wrapper's own `staleMaxAge: 0` reaches this path like any other resolved lifetime but can never be advertised: it exists only when the handler set `Cache-Control: must-revalidate`, i.e. exactly when the `has("cache-control")` check has already suppressed synthesis
- What is emitted: `max-age=<lifetime>` whenever a lifetime is present (`0` included), `s-maxage=<the same number>` additionally under `swr`, and `stale-while-revalidate=<staleMaxAge>` only when a stale window is actually named. **`max-age` accompanies `s-maxage` rather than being replaced by it** (finding 10.3) — `s-maxage` is shared-cache-only and overrides `max-age` there (RFC 9111 §5.2.2.10), so CDNs see no change, but a private cache got no freshness lifetime at all and fell back to heuristic freshness over `Date − Last-Modified` (§4.2.2), which is ≈ 0 because `last-modified` is stamped at fill time: browsers revalidated on **every** navigation while ocache held the entry for the full `maxAge`. The same number on both, because that is the number ocache enforces — a smaller one is unenforced fiction, a larger one an overclaim. `s-maxage` is kept rather than folded away (a lone `max-age` would already govern shared caches) because it is separately what authorizes a shared cache to store the response to an `Authorization`-carrying request (§3.5, reachable under `allowAuthorization`); `sendCacheControl: false` stays the way to advertise neither
- **Never a bare `stale-while-revalidate`** (finding 10.4): RFC 5861 §3 requires the delta-seconds, so the argument-less token the ISR shape (`swr` with no `staleMaxAge`) used to emit was unparseable and had to be ignored wholesale (RFC 9111 §5.2.3) — the stale window evaporated downstream while the header read as though it hadn't. **Nothing replaces it**, deliberately: that shape's stale window is genuinely _unbounded_ (the entry is merely retained until the backend evicts it by capacity — see the `cache.ts` lifetimes bullet), so no number states it, and an invented one (`maxAge`, a year) would advertise a stale window ocache never promised — the finding-10 failure mode over again, in the permissive direction. Silence is the strict direction and costs nothing real: a downstream cache revalidates when `max-age` runs out, ocache answers _that_ request from its retained stale copy while refreshing in the background, so ISR still happens — one layer in, where it is actually enforced. `{ swr: true, maxAge: 60 }` therefore advertises `max-age=60, s-maxage=60`, and `docs/1.guide/9.isr.md` documents that string
- `maxAge` is treated **identically** with and without `swr` — present (`0` included) is advertised, absent is not. The two synthesis branches disagreed (`!= null` under `swr`, truthy without it), so `{ swr: true, maxAge: 0 }` shipped `s-maxage=0` while `{ maxAge: 0 }` shipped nothing. Agreeing on `!= null` also means `validate` reads the same zero-lifetime opt-out out of a synthesized header as out of a hand-written one, so **`maxAge: 0` keeps the response out of storage either way** (it already did under `swr`), a dynamic one from `getMaxAge` included. A deliberate, narrowing storage change: `cache.ts` clamps a `<= 0` TTL to "re-resolve on every access", so the entry this replaces was written already expired and the handler ran on every request either way — what changes is a dead entry no longer being stored, plus an honest `max-age=0` downstream where silence previously invited heuristic caching. The opposite reconciliation (both branches skipping a zero) would have _started_ storing `{ swr: true, maxAge: 0 }` and serving it stale — widening, and the wrong direction to pick silently. The `!= null` guard on `maxAge` is defensive only: a handler's merged `maxAge` is always a number (the default is `1`, and an explicit `undefined` reads as unset — see the `cache.ts` bullet), and a `getMaxAge` that resolves nothing falls back to it, so "absent" is unreachable. The one on `staleMaxAge` is load-bearing — it _is_ the ISR shape above
- `sendCacheControl: false` opts out of `cache-control` synthesis entirely (**server-only caching**, issue #49 / nitro#3997): the entry is still stored and served from cache (SWR/`etag`/`last-modified` unaffected), but no `Cache-Control` is advertised to clients/CDNs — without the `no-store`/`private` tricks that would also disqualify the entry from storage via `validate`. Only governs ocache's own synthesis (checked in the internal `serialize` hook); a `cache-control` the handler set explicitly is left untouched and still sent
- Emits a `Vary` response header, merging with any `Vary` the handler already set (case-insensitive dedup, wildcard `*` left untouched — such a response is refused by `validate` anyway, so what `appendVary` preserves there is only what the direct caller is served) so downstream caches store per-variant. **Two separate lists, deliberately not the same one**: `keyHeaderNames` composes the cache key (and gates handler visibility of the credential headers), `varyHeaderNames` is the advertisement. They differ on exactly one name — `cookie` — which `allowCookies` removes from the key list (the key carries a finer `cookie.<hash(subset)>` component instead) but which must stay in the `Vary` list, since the response genuinely varies by the `Cookie` request header and `Vary` has no granularity below a header name. Conflating them meant an `allowCookies` route advertised `s-maxage`/`max-age` with **no** `Vary` at all, so a CDN stored one visitor's variant and served it to everyone; and `varies: ["cookie"] + allowCookies` silently dropped a `Vary` the caller had explicitly asked for. Deduped, so `varies: ["cookie"]` plus an allowlist emits `cookie` once. `allowQuery` contributes nothing to `Vary` (query lives in the URL, which downstream caches already key on). **Documented trade**: `Vary: Cookie` is destructive to CDN hit rates (any unrelated analytics/A-B cookie makes a request its own variant) — the honest version of a shared-cacheability claim ocache previously hadn't earned. Callers who need downstream hit rate should key by URL (`allowQuery`/path) instead of by cookie, or keep the cookie-keyed cache server-only with `sendCacheControl: false`. Rejected alternative: keep `Vary` off and mark cookie-keyed responses `private` — preserves CDN behavior by opting out of it rather than by telling the truth, and `private` also disqualifies the entry from ocache's own storage via `validate`
- **A handler's own `Vary` is now read, not only written** (finding 13, fail-closed half): `hasUnkeyedVary(vary, varyHeaderNames)` rejects in `validate` and suppresses synthesis in `serialize` — one shared predicate at both sites, exactly as the status and `Vary: *` gates are. ocache _wrote_ `Vary` but never _read_ one, so a handler declaring `Vary: Accept-Language` (the spec-correct way to say "this response is not interchangeable", RFC 9111 §4.1) had its English rendering stored under the language-free key and served to every other language — with that same `Vary` attached for downstream caches to propagate, the layer closest to the origin violating what it told everyone else. Compared against **`varyHeaderNames`, not `keyHeaderNames`**: the two differ only on `cookie`, which `allowCookies` keys as the finer `cookie.<hash(subset)>` component, so every name on the advertisement list _is_ in the key in some form and a handler declaring `Vary: Cookie` under `allowCookies` must still cache. Case-insensitive and whitespace-tolerant against a list `config.ts` already lowercases; only empty list elements are skipped (RFC 9110 §5.6.1 — a trailing comma isn't degenerate), so a malformed token matches nothing and rejects — **fail closed**. `*` is deliberately _not_ handled in this predicate: it is a different verdict on the same header, `hasVaryWildcard`'s (finding 08), applied alongside at both sites — folding it in would let a degenerate `varies: ["*"]` make the wildcard "keyed". Applied on read too, so an entry written by an older ocache heals on access. **Breaking behavior change**: it costs hit rate on a route whose `varies` doesn't match what its handler declares, which is exactly the route that was serving the wrong body — the fix is to make the two agree. That includes a custom `getKey` that already partitions by the header: `varies` is what this reads, so list the name there too (with a custom `getKey` that only widens the advertisement and forwards the header — the key is untouched). **Full `Vary` support** (folding the response's declared names into the key) is deliberately not attempted: `Vary` is only known _after_ the handler has run, so it needs a re-key or a second store pass — the classic two-phase problem, tracked as an open decision
- Honors the handler's **response-side opt-outs** — never cached (rejected in `validate`), though still returned to the caller: `Cache-Control: no-store` / `private` / `no-cache` / a zero **shared** lifetime, and `Vary: *`. Which directive states that lifetime follows RFC 9111 §5.2.2.10: **`s-maxage` overrides `max-age` for a shared cache** and ocache is one, so directives are collected first and only then judged — `s-maxage` governs whenever it parses, `max-age` otherwise, and only that effective value being `<= 0` rejects. Rejecting on the first zero of either (the shape this landed as) refused `public, max-age=0, s-maxage=600` — the canonical "browsers revalidate, CDN caches" idiom, a request _to_ be stored — in both directive orders, while `s-maxage=0, max-age=600` must still reject. Only `no-store`/`private` used to be recognized, so `no-cache` and a zero `max-age` — the two commonest ways a developer writes "don't reuse this", and what `"/**": { swr: 60 }` puts every hand-marked page behind — were stored and replayed while the directive was faithfully echoed to the client: the response advertised non-reusability while ocache was already sharing it (same shape as h3#1524 finding #15, one directive over). `no-cache` is **rejected outright**, not stored-with-revalidation: RFC 9111 §5.2.2.4 permits storing it if every reuse revalidates first, which is real new machinery (ocache has no foreground-revalidation path — no conditional request to the handler, no 304-refreshes-the-entry step) and buys nothing until that exists; a `TODO` at the branch records it. Directives are **parsed**, never substring-matched (`cacheControlDirectives`, quoted-string aware so `no-cache="set-cookie, x"` is one directive; `deltaSeconds` is RFC 9111 `1*DIGIT`, so `max-age=0600` is 600s and `stale-while-revalidate=0` is not a zero lifetime; a malformed value states nothing and is ignored, except a leading `-` which reads as already-expired). The qualified `no-cache="field"` / `private="field"` forms are rejected like the bare ones: they scope the ban to the named fields, but ocache replays a stored header set verbatim, so honoring them would mean stripping fields on every reuse. `Vary: *` lives in the same predicate (finding 13) but reads the `Vary` header, not `Cache-Control` — so `forbidsSharedCaching` takes the whole serialized header set and delegates to `cacheControlForbidsReuse`, rather than pretending it inspects one header. The rest of finding 13 (`hasUnkeyedVary`) is a **separate** check in `validateEntry`, deliberately not another arm of this predicate: such a response forbids nothing — it is cacheable, ocache just can't key it. All of this only governs storage: concurrent requests are still coalesced by cache key, so per-user responses must be keyed correctly (e.g. via `varies`)
- `Cache-Control: must-revalidate` is **not** an opt-out — it constrains stale serving, not storage (RFC 9111 §5.2.2.2) — so it must not reject. Instead the internal `getMaxAge` hook (which wraps the caller's, keeping their numbers) persists **`staleMaxAge: 0` on that entry**: `cache.ts`'s read path then computes `staleTtl === 0` → `swr = false` for that entry alone, so a fresh read is still a HIT and an expired one revalidates in the **foreground** instead of serving stale. Chosen over a new `CacheEntry.mustRevalidate` flag because "no stale window" is already exactly what `staleMaxAge: 0` means (the option is documented as "stale is never served"): no new field, no `cache.ts` change, and it flows through the storage-TTL and `expireCache` math for free — all of which already prefer the per-entry value, and all of which a flag would have to be taught separately. Consequence of always installing the hook: `cache.ts` now always writes `entry.maxAge`/`entry.staleMaxAge` for handlers (usually `undefined`, which falls back to the static options) — which is also what lets `serialize` advertise the per-entry lifetime unconditionally (finding 10.2). The wrapper computes its own override **first and independently**, and isolates the caller's hook in its own `try` (reported through the same `onError`/`console.error("[cache] getMaxAge hook error.")` shape `cache.ts` uses, so it is neither silent nor double-reported): `cache.ts` handles a throwing hook by leaving _both_ values `undefined`, so awaiting the caller's hook first and uncaught let one throwing caller hook take ocache's own `staleMaxAge: 0` down with it and the entry was served STALE — exactly what `must-revalidate` forbids. A throw degrades to "no _caller_ override", never to "no override at all". `proxy-revalidate` is the shared-cache counterpart and belongs in the same place, but is deliberately left to a separate change
- Cookies, response side: **no `Set-Cookie` ever survives a cacheable route** — unconditional `res.headers.delete("set-cookie")` in `serialize`, before storage and before the value any caller (including the direct MISS caller) receives. Closes issue #61: concurrent same-key requests coalesce onto one resolution, so the leader's per-request `Set-Cookie` (e.g. a session id) used to be replayed to every deduplicated peer — a cross-user session leak. `allowCookies` used to except its own names from the strip, which reintroduced that leak one opt-in later: a handler minting `sid` on first visit stored the response under the _no-sid_ key with `Set-Cookie: sid=s1` attached, so every subsequent first-time visitor (also no `sid`, same key) got a HIT carrying `sid=s1` — session-fixation grade, and broad rule sets like `"/**": { swr: 60 }` put every cookie-setting route there (h3#1524 audit, finding #15c). The more permissive alternative (refuse to _store_ a response that mints a cookie) can't close the concurrent-peer case at all — coalesced callers share one resolution and are indistinguishable — so the rule is uniform and one sentence long. The rest of the response is cached normally (mirrors how CDNs / Varnish drop `Set-Cookie` on cacheable responses). A bare `delete` covers every runtime, so the old `getSetCookie()` capability branch (needed only to keep allowlisted names) and the `_cookieName` helper are gone. `validate` rejects **any** stored `set-cookie` — defense-in-depth for pre-existing/foreign entries, incl. ones written by an older ocache that kept allowlisted cookies. **Breaking**: handlers that mint per-request cookies must serve them from a non-GET/HEAD (bypassed) route, where the response passes through untouched — allowlisting is no longer an option
- Cookies, request side: **by default no cookies participate in caching** (secure default) — the `Cookie` header is stripped before the handler runs and never varies the key. Two opt-ins, coarse and fine, both governing **this direction only**:
  - `varies: ["cookie"]` — the **coarse** opt-in, exactly symmetric with how `varies: ["authorization"]` already equals `allowAuthorization: true`: `cookie` stays in `keyHeaderNames`, so the **raw** `Cookie` header composes the key _and_ is forwarded to the handler untouched. Correct by construction (the key covers exactly what the handler can see) and the caller owns the fragmentation cost — one entry per distinct raw `Cookie` header value, i.e. effectively per visitor once any analytics/consent cookie is in play. Previously the raw header was hashed into the key while narrowing still stripped it, so the handler rendered the cookie-less default variant into every per-cookie entry (N identical entries, zero variation), a key re-derived from an already-served event drifted away from the one just written (so `.invalidate(event)` after `handler(event)` — the documented issue-#71 pattern — silently purged nothing), and the documented "`varies` headers are forwarded to the handler" rule was contradicted
  - `allowCookies: string[]` — the **fine** opt-in and the one to prefer: only the listed names survive in the handler-visible `Cookie` header and vary the key (sorted, order-independent — `filterCookie`). **Supersedes** `varies: ["cookie"]` in both directions — `cookie` is dropped from `keyHeaderNames` (the allowlist hash is strictly finer than the raw header) and the handler sees the filtered subset, never the raw header — but is added to `varyHeaderNames`, so setting `allowCookies` always emits `Vary: Cookie`, with or without a `varies` entry (see the `Vary` bullet for the CDN hit-rate consequence)
  - The three-way branch lives in the request-narrowing block: allowlist → filtered subset; no allowlist but `cookie` in `keyHeaderNames` → forward raw; neither → strip. One rule, shared with the credential headers: **a handler may read exactly what the key covers**
- Authorization: **by default `authorization` / `proxy-authorization` do not participate in caching** (secure default, same rigor as cookies) — both are stripped from the handler-visible request on cacheable calls, so a handler cannot render per-user content from a credential that isn't in the cache key. Previously they were forwarded untouched but never keyed, so a token-authenticated route failed **open**: the first caller's private response was stored under the anonymous key, replayed to everyone, and advertised `max-age=N, s-maxage=N` for shared CDNs (cookie-authenticated routes already failed safe — that asymmetry was the defect). `allowAuthorization: true` opts both names back in by folding them into both header lists (deduped against `opts.varies`, sorted), which in one step makes them vary the key, appear in the response `Vary`, and stay visible to the handler. Listing either name in `varies` counts as the same opt-in. Callers opting in own the consequence: one entry per distinct credential value, shared by everyone presenting it. A **breaking behavior change** — handlers needing the credential must set `allowAuthorization`, or bypass those requests (`shouldBypassCache`)
- Transport headers (`content-encoding`, `content-length`, `content-range`, `transfer-encoding`) are stripped in `serialize` before storage (`transportHeaders`): the body is stored fully decoded and re-buffered, so replaying an upstream `content-encoding: gzip` against a decompressed body (or a stale `content-length`/wire `transfer-encoding`) would desync the headers from the served body and yield malformed responses (nitro#2109). The runtime recomputes `content-length` from the served body on read. `content-range` is there for the same reason and **not** because a 206 could reach storage (it can't — `Range` requests bypass and `validate` rejects the status): it describes a _partial_ body, so on an entry we do store — always a complete representation — it is meaningless at best and a lie about the served bytes at worst. Realistic source: a proxying handler copying upstream headers onto a 200
- `varies` headers are **forwarded to the handler** — their values are part of the cache key, so reading them is safe and is the point of declaring them. **`cookie` is no longer an exception**: it too is forwarded (raw) when listed in `varies` with no `allowCookies`, which is what makes that listing a real opt-in rather than pure key fragmentation. They used to be the only headers filtered out, which meant `varies: ["accept-language"]` produced correct per-language keys and `Vary` while every entry held the _default_ rendering (**breaking behavior change**). Request narrowing is now driven by `keyHeaderNames` alone — a declared header is visible, an undeclared credential header (`authorization`/`proxy-authorization`/`cookie`) is stripped — plus the finer `allowCookies` filter and `allowQuery` on the URL
- Request narrowing (cookie stripping, authorization stripping, query narrowing) only applies to cacheable calls: non-GET/HEAD requests **and any request carrying a `Range` header** bypass the cache (the built-in half of `resolveBypass`, composed with any caller `shouldBypassCache`) and reach the handler with their request untouched — including the body, which the rewritten `Request` would otherwise drop. Gated on the **composed** verdict, never the built-in half alone (finding 09): the built-in check said "cacheable" for a GET the caller had excluded, so `shouldBypassCache` stripped credentials off the very requests it exempted from the cache — and it is the escape hatch the credential defaults document ("set `allowAuthorization`, or bypass those requests"), so following that advice served the anonymous/401 rendering to every authenticated user, on every request. `narrowRequest` gates itself rather than trusting its call site, so the two can't disagree. The verdict is produced **exactly once per call** — the caller's hook may be async, expensive or side-effecting — by `resolveBypass`, which `cache.ts` awaits to decide its short-circuit to the raw resolver and which memoizes the answer on the event in a per-handler-instance `WeakMap` (`config.bypassed`, the `searchCache` pattern) for the resolver to read. Per-call state keyed by the event, deliberately not a module-level "last verdict" slot, which would be a cross-request bug; threaded through `config` rather than through the resolver's arguments because `cache.ts` calls `fn(...args)` with the caller's args and nothing else. `narrowRequest`'s fallback to the built-in check covers only a resolver reached without `resolveBypass`, which `cachedFunction` cannot do. Narrowing **mutates the caller's event** (`event.req`, plus `event.url` under `allowQuery`) and never restores it, so after a MISS the caller observes the narrowed request while after a HIT or a bypass it does not — downstream middleware and logging see different headers depending on cache state. Not restored in a `finally` on purpose: a handler's body producer can run _after_ the resolver returns (an async `ReadableStream.pull` is drained by `serialize`'s `res.arrayBuffer()`), so a restore would hand the original credentialed request back to a lazy read whose output is then cached and replayed — re-opening exactly what narrowing exists to close. It would also still leave the SWR window, where the background refresh swaps the stale reader's event after its response was already returned. The real fix is to stop mutating the caller's event at all (hand the handler a narrowed copy), which needs a design decision because `E` is an arbitrary framework event — tracked separately
- **`Range` requests bypass the cache** (finding 07), whatever their method — the request-side half of the 206 fix, paired with `206`'s absence from the cacheable-status allowlist. `Range` is forwarded to the handler but is neither in the key nor a `Vary` dimension, so a range-honoring handler (static files, media, `serveStatic`) resolved a **partial** representation under the range-free key: one `curl -r 0-0` stored a one-byte body plus the `Content-Range` describing it, and every later `Range`-less GET was served that truncation for the whole TTL, propagated to shared CDNs by the synthesized `s-maxage` (RFC 9110 §15.3.7 / RFC 9111 §3.3 — a 206 answers only the request that named the range; combining/re-slicing partials is out of scope). Bypassing on the request side is the cheaper half: the handler never runs under a key, so nothing partial is stored, `serialize` never buffers a large partial body, and a ranged request can't thrash the plain entry. **Breaking behavior change**: a ranged request now also skips request narrowing (the standard bypass contract — untouched request in, live `Response` out) and gets no `x-cache`/`etag`/`cache-control` synthesis
- Bypassed responses pass through untouched: because `serialize` lives outside the resolver, a bypassed call (`cachedFunction` returns the resolver output raw — no `serialize`/`transform`) yields the handler's live `Response`, which the outer wrapper detects (`value instanceof Response`) and returns as-is. No body buffering (streaming/binary bodies survive), no synthesized cache headers, and no bogus `304` for a non-cacheable method — a **breaking behavior change** vs. the old always-serialize path (`fix(http)!`)
- `validate` rejects a **missing** body (`value.body === undefined`) but accepts `""`: a zero-byte 200 is a legal response and rejecting it would only cost hit rate. The dangerous empty body (a body-less HEAD response replayed to GET clients) is prevented by the method component in the key, not here — an empty entry is only readable by requests of the method that produced it. Documented in-place at the check so it isn't re-litigated
- **One status gate**, `isCacheableStatus` over the `cacheableStatuses` allowlist `{200, 203, 301, 308}` — the statuses whose response is a complete, reusable representation of what was requested. It replaced three overlapping conditions (`status >= 400`, the `nullBodyStatuses` set, and the implicit "anything under 400 is fine"), so `validate` now expresses "what may be stored" in exactly one place, which `serialize` also consults for the advertisement. Each exclusion is load-bearing: `302`/`303`/`307` are per-request answers (an auth middleware's `302 → /login?next=/dashboard` was stored under the **anonymous** `/dashboard` key — request-side defaults strip `Cookie`/`Authorization`, so anonymous and authenticated callers share a key — and published shared-cacheable, bouncing an authenticated user to someone else's login redirect); `206` is a partial body valid only for the range asked for (finding 07, request-side half in `shouldBypassCache`); `201`/`202`/`300` are operation outcomes or an unresolved choice; `204`/`205`/`304` have nothing to replay (a 304 in particular answers _one_ client's conditional request, so a crafted `If-Modified-Since: <far future>` used to store one that every later **unconditional** request got for the whole TTL, self-healing never); `>= 400` is unchanged from the old rule. **Strictly narrowing** — every allowlisted status was already cacheable, so nothing previously rejected became acceptable and no existing entry is invalidated. Caching `404`/`410` (RFC 9111 permits it heuristically) was considered and **declined**: it expands behavior and makes a 404 flood a cache-flush vector — finding 14.1's byte budget bounds what such a flood can _retain_, not the eviction pressure it applies to the hot set (finding 14.2). Rejecting on read as well as on write means an entry written by an older, more permissive ocache heals on first access
- `nullBodyStatuses` (`204`/`205`/`304`) survives for the **read path only** — the storage side is now just their absence from the allowlist. It is still needed there, and independently of `validate`: `serialize` stores a body-less response as `""` (not nullish, so `?? null` doesn't catch it), `new Response("", { status: 204 })` **throws**, and the MISS caller is served through the freshly serialized entry regardless of `validate`'s verdict — so without forcing `body → null` before `createResponse` every 204/205/304 would crash on the way out
- `.resolveKeys(event)` / `.invalidate(event)` / `.expire(event)` on the returned handler (issue #71) target the **resource, not one method variant**: they cover every cacheable method's variant of the event's resource key regardless of which method the passed event carries, so purging `/article/hello` can't leave a sibling HEAD entry advertising the dead etag/last-modified for downstream caches to revalidate against. `resolveKeys` enumerates the same set (one key per base prefix **per method variant**), the event's own variant first, so `keys[0]` is still exactly the key that event reads/writes. Implemented by feeding each variant key to the standalone `cache.ts` helpers as a fixed `getKey` — `resolveKey` is method-free, so no event is ever cloned or mutated. `variantOptions` calls `resolveStorage(_opts)` first: it spreads `_opts` into one fresh options object per variant, so without pre-resolving, a purge issued before the first request would leave each copy to resolve its own storage (re-running a `storage` factory once per variant)
- Storage memo asymmetry vs `cache.ts`: `defineCachedHandler` reassigns `opts` to a merged clone on entry and clones again into `_opts`, so **the caller's own options object never receives the resolved storage** — unlike `defineCachedFunction`, which writes it back to `_optsRef`. So `invalidateCache({ options: myHandlerOpts })` will _not_ reach a handler's default storage. Deliberate: never-works is clearer than sometimes-works (the memo would otherwise land only when a purge happened to run before the first request), and reconstructing a handler key by hand is the error-prone path issue #71 exists to avoid — use the handler's own `.invalidate(event)`/`.expire(event)`/`.resolveKeys(event)`, or pass an explicit `storage` if a standalone helper must reach it
- Framework integration hooks on `CachedEventHandlerOptions`:
  - `toResponse(value, event)` — convert handler return value to Response (default: plain Response constructor)
  - `createResponse(body, init)` — create the final Response from cached data (default: `new Response()`)
  - `handleCacheHeaders(event, conditions)` — custom 304 conditional check (default: built-in if-none-match/if-modified-since)

### Storage (`storage.ts`)

- `StorageInterface` — minimal `get`/`set` with optional TTL
- Setting a nullish value (`null`/`undefined`) via `set` deletes the entry instead of storing dead weight
- `createMemoryStorage()` — in-memory Map-based implementation with TTL expiry
- **Two ceilings, LRU-evicted in one loop: `maxSize` (10 000 entries) and `maxBytes` (100 MB, finding 14.1)**. They bound different things and both apply: `maxSize` bounds entry _count_, which is not a memory bound at all — retained bytes are `maxSize × whatever an entry weighs`, i.e. attacker-influenced for an HTTP handler. Measured: 10 000 × 1 MB documents held 10 GB of RSS, and because the cache is external/large-object memory the process is **OOM-killed rather than throwing a catchable `RangeError`** — there is no graceful degradation path to write. Promoted to a release blocker when finding 14.3 was rejected: `{ swr: true, maxAge: N }` (the documented ISR shape) carries an expiry but no storage TTL, so backend capacity became the _only_ bound on it — the backend therefore has to actually be one. `Infinity`/`0`/negative disables either, the same normalization `maxSize` already had; `get`'s recency touch is armed when _either_ ceiling is
- The budget is policed by a **running total**, not by recomputing (which would be O(cache) per write). That makes every removal path a correctness obligation: `set` (overwrite included), the nullish-value delete, `deleteEntry`, the TTL `setTimeout` callback and `get`'s lazy expiry all funnel through `deleteEntry`, which is the only place bytes are released, and the single `map.set` in `set` is the only place they are charged. A leaked count doesn't lose the budget, it converges on **evicting everything** — silently — so the drift is tested per path. `get`'s LRU touch deliberately uses raw `map.delete`/`map.set`: it moves the same entry object (and its charge), it is not a delete plus an insert
- **An entry larger than the whole budget is refused**, and any previous value under its key is dropped with it. The alternative — store it and sit permanently over the ceiling — isn't available, and evicting down to fit it flushes every other entry for something that _still_ doesn't fit, which is finding 14.2's cache-flush DoS reachable from a single request. Dropping the prior value is what `set` was asked to do; serving the old one afterwards would be a lie about what is cached, and the read simply misses and re-resolves. The eviction loop's empty-map guard makes termination unconditional regardless
- `sizeOf(value, key)` replaces the built-in estimate and owns the **whole** per-entry charge, key included — nothing is added on top. Only called when `maxBytes` is armed (an opted-out storage never pays for the walk). A throwing hook, or a result that isn't a finite non-negative number, falls back to the built-in estimate: the budget degrades to an approximation, never to "free"
- The built-in estimate is a **depth-limited, cycle-safe structural walk**, deliberately not `JSON.stringify(value).length` — that throws on cycles and BigInt, drops non-JSON values, and allocates a second copy of the very body being measured because it is large. The walk allocates nothing but its `seen` set and reads each string's `length` once, so the dominant real shape (`CacheEntry<ResponseCacheEntry>`, whose weight is `value.value.body` plus the header record, depth 3) costs a handful of property reads. `seen` charges any object once, so a cycle terminates and a shared subtree isn't double-counted; the depth cap (8) keeps recursion off the stack limit for pathologically deep values, at the price of under-counting below it — that is what `sizeOf` is for. Typed arrays/`ArrayBuffer` are charged `byteLength` (walking their indices would be both O(n) reads and wildly wrong) and `Map`/`Set` are iterated, since `Object.keys` would price them at zero — the dangerous direction. Host objects with no own enumerable properties (a `Response`) are likewise under-counted, which is why the HTTP layer stores the serialized entry, not the live response
- Strings are charged at **2 bytes per UTF-16 code unit** — the upper bound; engines store latin1-only strings at one byte per character, so an ASCII body is over-charged by up to 2×. Over-charging is the only safe direction: a budget that under-counts is not a bound, which is the whole failing being fixed. The key is measured the same way and counts toward the entry — the finding's second measurement (10 000 × 8 KB attacker-chosen _paths_, 93 MB heap / 296 MB RSS in 6 s, with trivial values) is entirely key weight
- `StorageOption` — `StorageInterface | (() => StorageInterface)`; the `CacheOptions.storage` type. Factory = late binding (handler defined at module load, backend configured at server start)
- `resolveStorage(...optsList)` — internal: resolves `optsList[0].storage` (factory → call it; unset → fresh `createMemoryStorage()`) and writes the result into every listed options object. Deliberately commented with `//`, not JSDoc, so docs4ts keeps it out of the generated API docs
- **No global storage.** `useStorage()`/`setStorage()` are _removed_ (not deprecated): the module-level slot made the last `setStorage()` call win for every consumer in the process, so two independent apps each building their own handler + storage shared one backend and served each other's cached response bodies (h3#1524 audit, finding #2). Per-instance defaults close it by construction — two defaults can never collide on a key. Sharing is explicit: pass the same `storage`

### Types (`types.ts`)

- `HTTPEvent` — `{ req: Request; url?: URL }` (url falls back to `new URL(req.url)`)
- `EventHandler<E>` — `(event: E) => unknown | Promise<unknown>` (generic, defaults to HTTPEvent)
- `CacheEntry<T>` — stored cache entry with value, expires, mtime, integrity
- `CacheOptions<T>` — maxAge, swr, staleMaxAge, getMaxAge (dynamic per-entry TTL hook), serialize (write-time hook, mirrors `transform`), resolverTimeout (ms deadline on one shared resolution, default 30 000), base (string | string[] for multi-tier), storage (`StorageOption`; per-instance, defaults to a fresh memory storage), getKey, validate, transform, etc.
- `CachedEventHandlerOptions<E>` — extends CacheOptions with headersOnly, varies, allowQuery, allowCookies, allowAuthorization, toResponse, createResponse, handleCacheHeaders
- `CacheConditions` — `{ modifiedTime?, maxAge?, etag? }` passed to handleCacheHeaders hook
- `ResponseCacheEntry` — serialized response (status, statusText, headers, body; optional `base64` flag when `body` is base64-encoded binary)

## Design Decisions

- No h3/srvx/unstorage dependency — fully standalone
- `waitUntil` is typed as optional on `ServerRequest` (`event.req`) — runtime-specific (srvx ServerRequest, Cloudflare), accessed via `event?.req.waitUntil?.(promise)`. `http/request.ts`'s narrowing replaces `event.req` with a fresh `Request`, so it carries `waitUntil` over alongside `runtime`, **bound to the original request** (a bare copy would run with the narrowed `Request` as its receiver; srvx/Cloudflare implement it against the real one). All four `cache.ts` call sites — cache write, SWR background refresh, and both evictions — read `event.req.waitUntil` _after_ that swap, so dropping it made every background write inert on exactly the runtimes that provide it: the isolate can be torn down before the write lands, i.e. every request a MISS forever, with SWR refreshes and post-failure evictions cancelled the same way
- `event.url` is optional — the `http/` modules fall back to `new URL(event.req.url)`
- Storage methods are `get`/`set` (not `getItem`/`setItem`)
- `base` supports `string | string[]` — multi-tier: reads try each prefix in order (first hit wins), writes go to all prefixes
- Default cache key group is `"functions"` (cache.ts) / `"handlers"` (http/index.ts) — no `ocache/` prefix
- Integrity hash excludes `base`, `group`, `name`, `storage` (storage-location fields) so entries remain valid across different base/backend configurations. Excluded in **both** `integrityOpts` (cache.ts and http/config.ts). Verified: ohash serializes a storage object's methods as source text, so two `createMemoryStorage()` instances hash identically (even with different `maxSize` — a closure variable) while a factory and a ready instance hash differently — i.e. including it would invalidate every entry on a purely cosmetic config edit while failing to distinguish genuinely different backends
- Storage is per cached function/handler, never global — see the `storage.ts` section. `setStorage()`/`useStorage()` were removed in the pre-1.0 cleanup (breaking)
