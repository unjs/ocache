# Cookies

**By default, cookies do not take part in caching in either direction.** This default is secure:

- ocache removes the `Cookie` request header before your handler runs. The handler cannot produce cookie-specific output that is then cached and served to someone else.
- Cookies never vary the cache key.
- ocache removes any `Set-Cookie` from your handler before it caches or returns the response.

These rules prevent a cookie for one request, such as a session ID, from reaching another visitor. They protect both later cache hits and concurrent requests that receive the same cached response.

You can allow request cookies individually with [`allowCookies`](#allowing-specific-cookies). You can allow the full request header with [`varies: ["cookie"]`](#varying-by-the-whole-cookie-header). **You cannot allow response cookies.** A `Set-Cookie` header never remains on a cacheable response. See [Setting cookies](#setting-cookies).

```ts
const page = defineCachedHandler(
  async (event) => {
    event.req.headers.get("cookie"); // always null for cached GET/HEAD requests
    return new Response(await renderPage(), {
      headers: { "content-type": "text/html" },
    });
  },
  { maxAge: 60 },
);
```

> [!NOTE]
> This applies only to cacheable requests (`GET` and `HEAD`). Methods that fully bypass the cache, such as `POST` and `PUT`, reach the handler unchanged. Their cookies, headers, query, and body remain available. Their `Set-Cookie` header also passes through unchanged.

## Allowing specific cookies

Set `allowCookies` to a list of allowed cookie names. This allows specific **incoming** cookies. For these cookies only:

- They remain in the `Cookie` header that your handler receives.
- They vary the cache key. ocache sorts them, so their order does not matter, as with [`allowQuery`](/guide/query-params). Only the allowed subset becomes part of the key, not the full raw `Cookie` header.

ocache still removes all other cookies from the request. It caches the rest of the response as usual.

```ts
const page = defineCachedHandler(myHandler, {
  maxAge: 300,
  allowCookies: ["theme"], // theme=dark and theme=light cache separately; every other cookie is ignored
});
```

Cookie names are **case-sensitive**. `allowCookies` takes priority over `varies: ["cookie"]`. Set the allowlist and remove the broad `varies` entry. ocache emits the `Vary: Cookie` header described below in both cases. If you set both options, the allowlist controls the request and the key. The key includes only the allowed subset, and the handler receives the filtered header instead of the raw header.

Allow only cookies whose values select a valid _representation_, such as a `theme` or `locale` preference. Do not allow a per-user secret. All clients that send the same value share one entry.

## Varying by the whole `Cookie` header

You can list `cookie` in [`varies`](/guide/handler#varying-by-request-headers) without an allowlist. This is a broad form of the same opt-in. It is like listing `authorization` instead of setting [`allowAuthorization`](/guide/handler#credential-headers). In this case, the **raw** `Cookie` header:

- becomes part of the cache key as the full unmodified value,
- reaches your handler unchanged,
- is advertised as `Vary: Cookie`.

```ts
const page = defineCachedHandler(
  (event) => renderFor(event.req.headers.get("cookie")), // the full raw header
  { maxAge: 60, varies: ["cookie"] },
);
```

> [!WARNING]
> **This can create many cache entries.** In practice, one entry for each distinct `Cookie` header can mean one entry for each visitor. Any analytics, consent, or A/B cookie creates a separate variant. The cache can no longer combine these requests. Use `allowCookies` to key only on the few names that select a representation. Use `varies: ["cookie"]` only when the handler must read the full header.

### `allowCookies` emits `Vary: Cookie`

Setting `allowCookies` adds `Cookie` to the response [`Vary`](/guide/handler#varying-by-request-headers) header. ocache keys on a hash of the allowed subset. However, `Vary` can specify only the full header name. It cannot tell a CDN that only the `theme` cookie matters.

```http
Cache-Control: max-age=300, s-maxage=300
Vary: Cookie
```

This header describes the response correctly, but it has a cost:

> [!WARNING]
> **`Vary: Cookie` greatly reduces hit rates for CDNs and shared proxies.** Almost every visitor has a cookie, such as an analytics, A/B, or consent cookie. Each distinct `Cookie` header becomes a separate downstream variant. As a result, shared caching almost stops. This does not affect your ocache entries because they key only on the allowed subset. It affects the cache _in front_ of ocache.

Before ocache v1, this header was omitted. A cookie-keyed route advertised `s-maxage` without `Vary`. CDNs cached the response and served **one visitor's variant to everyone**. This change can lower your downstream hit rate after an upgrade. The old behavior had a higher hit rate because it served incorrect content.

If you need a high downstream hit rate, **do not key by cookie**:

- Select the representation from the URL instead. Use a `?theme=dark` parameter with [`allowQuery`](/guide/query-params), or use a separate path. These options vary the key without changing `Vary`, so a CDN can cache each variant.
- Or keep the cookie-keyed ocache entry without a synthesized downstream freshness lifetime. Use [`sendCacheControl: false`](/guide/cache-control). This option does not emit `no-store` or guarantee that browsers and CDNs refuse storage.

## Setting cookies

**`allowCookies` does not affect the response. A `Set-Cookie` header never remains on a cacheable (`GET` or `HEAD`) route.** ocache removes it from the stored entry and from the response that the caller receives. This includes the caller whose request produced the response.

You cannot turn off this behavior. A cached response is shared. ocache replays it to each later request that uses the same key. It also returns it to concurrent callers that share one handler call. A cookie created in that response would reach people for whom it was not created. Allowing a cookie name would make this data leak possible with one opt-in:

```ts
// Even with allowCookies: ["sid"], the Set-Cookie below never reaches any caller.
const page = defineCachedHandler(
  () => new Response("hello", { headers: { "set-cookie": `sid=${newSessionId()}` } }),
  { maxAge: 60, allowCookies: ["sid"] },
);
// First visitor:  MISS, no Set-Cookie.
// Second visitor: HIT (same key — neither had a `sid`), no Set-Cookie.
// Previously both received `sid=<the first visitor's id>` — a session-fixation hole.
```

To create a cookie for one request, use a request that bypasses the cache. Only `GET` and `HEAD` are cacheable. A `POST`, or any request excluded by `shouldBypassCache`, reaches the handler unchanged. Its `Set-Cookie` header also remains unchanged:

```ts
const login = defineCachedHandler(
  async (event) => {
    if (event.req.method === "POST") {
      // Bypassed: this Set-Cookie is neither stored nor shared.
      return new Response("ok", {
        headers: { "set-cookie": `sid=${await startSession(event)}; HttpOnly; Path=/` },
      });
    }
    return new Response(await renderLoginPage());
  },
  { maxAge: 60 },
);
```

## Caveats

- **Custom `getKey`.** As with `allowQuery`, a custom `getKey` fully controls the cache key. Allowed cookies no longer vary it automatically. If your handler output depends on a cookie, add that cookie to `getKey`. ocache still filters the `Cookie` header that the handler receives to the allowlist.
- **Entries written by older versions.** ocache refuses to serve a stored response that contains `Set-Cookie`. An older ocache version might have cached this response when it kept allowed cookies. After you upgrade, ocache cannot replay that response from existing storage.
