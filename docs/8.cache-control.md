# Cache-Control & Eligibility

`defineCachedHandler` creates a `Cache-Control` header for cacheable responses. It does not override a header that the handler sets. It also follows built-in eligibility rules. This page explains how to keep responses out of the cache. It also explains how to separate server-side storage from client caching and how to add eligibility rules.

## What is never cached

Before ocache stores a response, it applies these built-in checks. If a response fails **one or more** checks, ocache still returns it to the caller. It never stores or serves that response from the cache:

- **A status other than `200`, `203`, `301`, or `308`** — ocache uses an explicit allowlist. It does not store every response that is not an error. These four statuses provide a complete, reusable representation of the requested resource. ocache rejects all other statuses. This includes `4xx` and `5xx` because an error is not a representation. It includes `201`, `202`, and `300` because they describe an operation result or an unresolved choice. It includes `204`, `205`, and `304` because they have nothing to replay. In particular, a `304` answers one client's conditional request. It includes `206` because the partial body is valid only for the requested range. It also includes temporary redirects `302`, `303`, and `307` because they can be specific to one request. For example, if ocache stored an authentication redirect to `/login` under an anonymous key, it would serve that redirect to all requests for the URL.
- **A `Cache-Control` opt-out from the handler** — ocache honors `no-store`, `private`, `no-cache`, or a zero **shared** lifetime. It uses `s-maxage` when present and `max-age` otherwise. See [Private / non-cacheable responses](#private--non-cacheable-responses).
- **`Vary: *`** — this is the strongest "do not share this" signal other than `no-store`. No stored response can match such a request (RFC 9111 §4.1). ocache keeps one entry for each cache key, so it must reject the entry.
- **A `Vary` that names a request header outside the cache key** — `Vary` states that responses are not interchangeable (RFC 9111 §4.1). ocache keys only on [`varies`](/guide/handler#varying-by-request-headers) and `Cookie` under [`allowCookies`](/guide/cookies). If a handler returns `Vary: Accept-Language` without `varies: ["accept-language"]`, ocache could replay the first language to all other languages. Instead, it rejects the entry. ocache caches a response normally when `Vary` names only headers already in the key. Make the two lists agree. See [Varying by request headers](/guide/handler#varying-by-request-headers).
- **A missing body** — there is nothing to replay. A zero-byte body is different. An empty `200` is valid and caches normally.
- **An `etag` or `last-modified` with the literal string `"undefined"`** — a handler can create this value when it converts a missing value to a string. ocache creates both headers when the handler omits them, so a genuinely missing header never reaches this check. ocache rejects the placeholder because it would break conditional requests.

These checks always apply. You cannot turn them off.

If the built-in checks reject a response, ocache also does **not synthesize `Cache-Control`**. The only exception is `shouldCache`, which is described below. For example, ocache returns a `500` without synthesized `Cache-Control`. A shared cache before your handler cannot keep the error for `maxAge + staleMaxAge` while ocache runs the handler for every request. The same rule applies when ocache rejects a response because of `Vary: *` or a header outside the cache key. These responses might have no `Cache-Control` of their own, so suppressing the synthesized header is especially important. A `Cache-Control` opt-out needs no special handling. The handler already set that header, and ocache never overrides it for any status. The client receives the handler directive.

[`shouldCache`](#custom-eligibility-shouldcache) is the exception. If your hook rejects a response, ocache still advertises the synthesized lifetime. This supports a valid setup in which ocache does not store a response but a CDN can store it. `sendCacheControl: false` suppresses ocache's synthesized downstream freshness lifetime while ocache still stores the response. It does not emit `no-store` or prevent downstream storage. To set an explicit downstream policy, set `Cache-Control` on the response.

## What is advertised

When the handler does not set `Cache-Control`, ocache creates one from the lifetime that it enforces for the entry:

| Options                                       | Synthesized `Cache-Control`                           |
| --------------------------------------------- | ----------------------------------------------------- |
| `{ maxAge: 60 }`                              | `max-age=60`                                          |
| `{ maxAge: 60, swr: true }`                   | `max-age=60, s-maxage=60`                             |
| `{ maxAge: 60, swr: true, staleMaxAge: 600 }` | `max-age=60, s-maxage=60, stale-while-revalidate=600` |
| `{ maxAge: 0 }`                               | `max-age=0` — a zero lifetime, so nothing is stored   |

Important details about this header:

- **`max-age` uses the same value as `s-maxage`.** `s-maxage` applies only to shared caches and overrides `max-age` in those caches (RFC 9111 §5.2.2.10). Because both values match, adding `max-age` does not change CDN behavior. A browser does not use `s-maxage`. Because ocache sets `last-modified` when it fills the entry, heuristic freshness (§4.2.2) is close to zero. Previously, private caches revalidated on every navigation while the server kept the entry for the full `maxAge`. They now receive the same freshness lifetime that ocache enforces. This is the only lifetime that ocache can promise.
- **ocache sends `stale-while-revalidate` only with a value.** The directive requires a number of seconds (RFC 5861 §3). The [ISR pattern](/guide/isr), which uses `swr: true` without `staleMaxAge`, has an unlimited stale window. No number can describe it correctly, so ocache does not advertise the directive. A downstream cache revalidates when `max-age` ends. ocache responds from its stale copy while it refreshes in the background. ISR behavior stays the same, but the downstream cache does not manage it. Before v1, ocache sent `stale-while-revalidate` without a value. Compliant caches must ignore that form, so it did not advertise the window.
- **[`getMaxAge`](/guide/api) controls each field.** A per-entry `maxAge` or `staleMaxAge` overrides the static option in the header. It also overrides the option in the freshness check and storage TTL. If the hook omits a field, ocache uses the static option for that field. For example, a 2-second window from the hook is advertised as `max-age=2`, even with `{ maxAge: 3600 }`. The downstream lifetime always matches the lifetime that ocache enforces.

`sendCacheControl: false` turns off this behavior. See [Suppress synthesized freshness](#suppress-synthesized-freshness-sendcachecontrol). ocache never changes a `Cache-Control` header that the handler sets.

## Private / non-cacheable responses

To keep a response out of the cache from inside the handler, set an appropriate `Cache-Control` directive. ocache honors all directives in this table. It returns the response with the header unchanged, but never stores or serves the response from the cache:

| Directive                  | Meaning                                        |
| -------------------------- | ---------------------------------------------- |
| `no-store`                 | Never store this anywhere.                     |
| `private`                  | Not in a shared cache — and ocache is one.     |
| `no-cache`                 | Must not be reused without revalidating first. |
| `max-age=0` / `s-maxage=0` | Stale the moment it was produced.              |

ocache parses directives instead of matching substrings. For example, `max-age=0600` means 600 seconds. A `0` in a different directive, such as `stale-while-revalidate=0`, does not mean a zero lifetime.

`s-maxage` overrides `max-age` for shared caches (RFC 9111 §5.2.2.10). ocache is a shared cache, so only `s-maxage` controls it when both directives are set. ocache stores `public, max-age=0, s-maxage=600` for 600 seconds. This tells browsers to revalidate and shared caches to keep the response for 10 minutes. ocache does not store `public, s-maxage=0, max-age=600`.

> [!NOTE]
> The same rule applies to the header that ocache creates. `maxAge: 0`, or a `getMaxAge` result of zero, advertises a zero lifetime. The header contains `max-age=0`, plus `s-maxage=0` with `swr`. ocache stores nothing because an entry with a zero lifetime expires immediately. The handler runs for every request. An omitted option or an explicit `undefined` uses the default of `maxAge: 1`. Only an actual value of `0` opts out.

```ts
const dashboard = defineCachedHandler(
  async (event) => {
    // Readable only because of `allowAuthorization` below — see the warning
    const user = await getUser(event.req.headers.get("authorization"));
    if (!user) {
      return new Response("Please log in", { status: 401 });
    }
    // Personalized — never cache this one
    return new Response(renderDashboard(user), {
      headers: {
        "content-type": "text/html",
        "cache-control": "private",
      },
    });
  },
  {
    maxAge: 300,
    allowAuthorization: true, // the credential varies the key *and* reaches the handler
  },
);
```

ocache preserves any **other** `Cache-Control` from the handler without changes. It creates `max-age`, `s-maxage`, and `stale-while-revalidate` only when the handler does not set `Cache-Control`.

### The handler has to know who is asking

> [!WARNING]
> **A `private` response is only private when the handler can identify the caller.** For cacheable (`GET` and `HEAD`) requests, ocache removes [headers that the cache key does not cover](/guide/handler#headers-the-handler-cant-see) **before it runs the handler**. These headers include `Authorization`, `Proxy-Authorization`, and the full `Cookie` header. They also include other identity headers, such as `X-Api-Key` or a proxy-provided `X-Forwarded-User`. Without `allowAuthorization`, the preceding example cannot identify anyone. It renders the anonymous variant for every caller. In that example, the anonymous response is `401`, so the route does not work for anyone. The result is worse if the anonymous branch returns a public `200`. ocache stores that page under the shared key and serves it to logged-in users. The `private` branch never runs. The opt-out works correctly because `Cache-Control: private` keeps its response out of the cache. The problem is that the handler cannot distinguish callers.

The rule is: **a handler can read exactly what the cache key covers**. For a per-user response, add the caller identity to the key or keep the request out of the cache. You can use four methods for each route:

- **[`allowAuthorization: true`](/guide/handler#credential-headers)** — use this as shown in the example. Both credential headers vary the key, reach the handler, and appear in `Vary`. This is best when only _some_ route responses are personalized. The anonymous response still caches under its own key. The `private` responses require only a key computation because ocache never stores them.
- **[`shouldBypassCache`](/guide/handler#cacheable-requests)** — keep these requests fully out of the cache. A bypassed request reaches the handler **unchanged**, including credentials, cookies, the full query string, and the body. ocache returns the live response. It does not store the response or combine it with a concurrent request. It does not create `etag`, `Cache-Control`, or `X-Cache`. This is best when _every_ route response is per-user. In this case, the `private` header only gives instructions to the browser and CDNs because ocache does not process the response.

  ```ts
  const dashboard = defineCachedHandler(renderDashboardFor, {
    maxAge: 300,
    shouldBypassCache: (event) => event.req.headers.has("authorization"),
  });
  ```

- **[`allowCookies: [...]`](/guide/cookies)** — use this opt-in for session-cookie authentication. Only the listed cookie names remain in the `Cookie` header that the handler receives. Only these cookies vary the key. The trade-off is the same as for `allowAuthorization`. All callers with the same value share one entry. A response that must not be shared still needs `private` or `no-store`.
- **[`varies: [...]`](/guide/handler#varying-by-request-headers)** — use this general form for identities in another header, such as `X-Api-Key` or a proxy-provided `X-Forwarded-User`. It has the same trade-off. A truly private response must also contain `private`.

> [!IMPORTANT]
> An opt-out controls only what ocache **stores**. It does not divide the cache key. ocache still combines concurrent requests by cache key. Two callers that use one key receive the result of one handler call, even when ocache does not store it. Therefore, per-user responses need correct keys. Use [`allowAuthorization`](/guide/handler#credential-headers), [`varies`](/guide/handler#varying-by-request-headers), or [`allowCookies`](/guide/cookies). Alternatively, bypass the cache to skip keying and request combining.

> [!NOTE]
> ocache currently rejects `no-cache` instead of storing and always revalidating it. RFC 9111 §5.2.2.4 permits storage if the cache revalidates with the origin before every reuse. ocache does not currently have a foreground revalidation path. Therefore, storing the response would provide no benefit over not storing it.

## Never serve this stale (`must-revalidate`)

`must-revalidate` is **not** an opt-out. It limits stale serving, not storage. ocache stores a response with this directive and serves it normally while it is fresh. It never serves the response when it is stale, even with `swr: true` and a large `staleMaxAge`. After the entry expires, the next request revalidates in the **foreground** and waits for a fresh response:

```ts
const handler = defineCachedHandler(
  async () => {
    return new Response(await renderPrices(), {
      headers: { "cache-control": "public, max-age=60, must-revalidate" },
    });
  },
  { maxAge: 60, swr: true, staleMaxAge: 600 }, // SWR everywhere else, never for this response
);
```

Internally, ocache uses `staleMaxAge: 0` for that entry. [`getMaxAge`](/guide/api) uses the same method to give one entry its own lifetime. Therefore, the directive applies only to that response, not to the full handler.

## Suppress synthesized freshness (`sendCacheControl`)

Use this option when ocache should store a response without adding a downstream freshness lifetime. This does not define a complete downstream storage policy.

Set `sendCacheControl: false` to suppress the synthesized header. ocache still stores and serves the response. SWR, `etag`, and `last-modified` still apply:

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  swr: true,
  sendCacheControl: false, // no synthesized downstream freshness lifetime
});
```

This option controls only the header that ocache creates. ocache still preserves and sends a `Cache-Control` header that the handler sets. It also does not change `Vary` because `Vary` describes the response, not a cache directive. Without an explicit directive such as `no-store`, browsers and CDNs can still store the response under their own rules.

You can also use this option when [`allowCookies`](/guide/cookies) greatly reduces your CDN hit rate. A cookie-keyed route emits `Vary: Cookie`, which is difficult for downstream caches to use. `sendCacheControl: false` keeps the server-side cache and suppresses ocache's synthesized freshness lifetime.

> [!TIP]
> If `invalidateCache` or `expireCache` clears your storage but callers still get stale responses, a browser or CDN before the handler probably has its own copy. The synthesized `Cache-Control` lets it cache the response independently. A purge of server storage does not reach that cache. `sendCacheControl: false` suppresses this synthesized freshness lifetime, but it does not emit `no-store` or guarantee that downstream caches refuse storage.

## Custom eligibility (`shouldCache`)

Use `shouldCache` to add a rejection rule to the built-in checks. It receives the serialized response. Return `false` to skip caching. ocache still returns the response to the caller. For example, the built-in checks allow permanent redirects (`301` and `308`). You can use this hook to keep them out of the cache:

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  shouldCache: (res) => res.status < 300,
});
```

Important behavior:

- **Combined with the built-in checks using AND.** `shouldCache` can only reduce what ocache caches. It cannot force ocache to cache a response that fails a built-in check.
- **Can be async.** Return a `boolean` or a `Promise<boolean>`.
- **Also runs on reads.** It controls storage of a fresh response and serving of a stored response. This includes the stale-while-revalidate decision. Keep the hook fast, and use only the entry that it receives.
- **Fails closed.** If the hook throws, ocache treats the response as not cacheable and reports the error through `onError`.
