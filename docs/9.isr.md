# Incremental Static Regeneration

You can use `defineCachedHandler` for ISR-style behavior. It serves a cached page immediately. When the page becomes stale, it regenerates the page in the background. It continues to serve the last good version until the refresh completes.

```ts
const page = defineCachedHandler(
  async (event) => {
    const url = event.url ?? new URL(event.req.url);
    const html = await renderPage(url);
    return new Response(html, { headers: { "content-type": "text/html" } });
  },
  {
    swr: true, // serve stale instantly, refresh in the background
    maxAge: 60, // "revalidate" window: fresh for 60s, then refresh on next request
    // no staleMaxAge → the last good page is served until a refresh replaces it
  },
);
```

Two options create ISR-like behavior:

- **`swr: true`** turns on stale-while-revalidate. When an entry is older than `maxAge`, the next request gets the stale page immediately. A fresh render runs in the background.
- **Omit `staleMaxAge`.** This is important. Without this option, an entry never becomes too old to serve. ocache serves the last successful render until a refresh replaces it. This matches ISR. If you _set_ `staleMaxAge`, the stale period has a strict limit. After `maxAge + staleMaxAge`, ocache removes the entry. This sum is also the storage TTL. The next request waits for a fresh render.

> [!NOTE]
> When you omit `staleMaxAge`, an entry has no storage TTL. It **remains until the storage backend evicts it**. The backend capacity, not a timer, limits cache growth. The built-in [`createMemoryStorage`](/storage) evicts the least recently used entries above **10 000 entries or 100 MB** (`maxSize` or `maxBytes`). Set these limits for the pages that you serve. An external backend needs its own capacity limit. Alternatively, set `staleMaxAge` to allow eventual cleanup, but this changes the exact ISR behavior.

With this config, the handler also emits `Cache-Control: max-age=60, s-maxage=60`. A cache in front of it revalidates on the same schedule. **This config does not advertise `stale-while-revalidate`.** The directive requires a number of seconds (RFC 5861 §3). This config has an unlimited stale window, so no number would be correct. A downstream cache revalidates after 60 seconds. ocache immediately responds from its retained copy and regenerates the page in the background. Thus, ISR runs where ocache enforces it. If you set `staleMaxAge`, the window has a number. ocache then advertises `max-age=60, s-maxage=60, stale-while-revalidate=<staleMaxAge>`. See [what is advertised](/cache-control#what-is-advertised) for the full table.

> [!NOTE]
> If your handler sets `Cache-Control`, ocache does not change or synthesize it. ocache also reads this header. An opt-out (`no-store`, `private`, `no-cache`, or `max-age=0`) keeps the page out of the cache. `must-revalidate` keeps the page cached but prevents stale serving. This turns off ISR for that page. See [Cache-Control](/cache-control).

## On-demand revalidation

The handler from `defineCachedHandler` provides `.expire()`, `.invalidate()`, and `.resolveKeys()`. These methods are similar to Next's `revalidatePath` and `revalidateTag`. Each method takes the request `event` and gets the exact cache key from it. You do not have to rebuild the key:

```ts
const page = defineCachedHandler(
  async (event) => {
    const url = event.url ?? new URL(event.req.url);
    return new Response(await renderPage(url), {
      headers: { "content-type": "text/html" },
    });
  },
  { swr: true, maxAge: 60 },
);

// ISR-style: serve the stale page once more, refresh in the background
await page.expire(event);

// Hard purge: next request blocks on a fresh render
await page.invalidate(event);
```

Use `.expire()` for ISR behavior without blocking visitors. Use `.invalidate()` only when the next reader must get a guaranteed fresh render. See [Invalidation & Expiration](/invalidation) for the detailed behavior.

> [!TIP]
> These methods use the event in the same way as the handler. This includes request values for `varies`, `allowQuery`, and `allowCookies`. Pass an event that matches the variant that you want to revalidate. The request **method** is the exception. `GET` and `HEAD` use separate cache keys, but revalidating either method purges both entries. Therefore, a page cannot keep a stale `HEAD` entry. To revalidate without an event, such as from a webhook or cron job, use the standalone [`expireCache` / `invalidateCache`](/invalidation) helpers. They rebuild the key from options.

## Per-route revalidate windows

If pages need different refresh intervals, use `getMaxAge` to get the window from the response. This is similar to Next's `revalidate` for each fetch. For example, your handler can set an `x-revalidate` header. In `getMaxAge`, `entry.value` is the standard `Response`. The `getMaxAge` hook defines the lifetime, so you do not need a static `maxAge`. If the hook does not give a response a lifetime, ocache uses the static option. This is the 1-second default unless you set it:

```ts
const page = defineCachedHandler(
  async (event) => {
    const url = event.url ?? new URL(event.req.url);
    const { html, revalidate } = await renderPage(url);
    return new Response(html, {
      headers: { "content-type": "text/html", "x-revalidate": String(revalidate) },
    });
  },
  {
    swr: true,
    getMaxAge: (entry) => {
      const revalidate = entry.value.headers.get("x-revalidate");
      return revalidate ? Number(revalidate) : 60; // missing header → default window
    },
  },
);
```

ocache also advertises the window that the hook returns. The page sends `Cache-Control: max-age=<revalidate>, s-maxage=<revalidate>` instead of the static option. Before v1, the synthesized header always used the static `maxAge`. Therefore, ocache regenerated on the hook schedule while upstream caches kept the page for the static lifetime.

## Differences from CDN-managed ISR

> [!NOTE]
> Three behaviors differ from CDN-managed ISR.
>
> 1. **ocache combines duplicate background refreshes for each instance**, not globally. With multiple servers or serverless instances, the origin can receive one refresh from each instance. If regeneration is expensive, add a distributed lock in your [custom storage](/storage).
> 2. **Entries do not expire automatically** when you omit `staleMaxAge`. This keeps the last good render available. It also lets storage grow until the backend evicts entries or you purge them with `invalidateCache`. `createMemoryStorage` evicts above 10 000 entries or 100 MB, whichever limit it reaches first. Set `staleMaxAge` to allow eventual cleanup, but this changes the exact ISR behavior.
> 3. **A browser or CDN can still serve stale content after a purge.** `invalidateCache` and `expireCache` clear only server-side storage. A client or CDN that cached the synthesized `Cache-Control` response does not know about the purge and continues to serve it. Set [`sendCacheControl: false`](/cache-control#suppress-synthesized-freshness-sendcachecontrol) to suppress ocache's synthesized downstream freshness lifetime. This option does not emit `no-store` or guarantee that downstream caches refuse storage.
