# Tracing

ocache publishes cached calls on two [`node:diagnostics_channel`](https://nodejs.org/api/diagnostics_channel.html) tracing channels, so an APM tool or a metrics library can see which cached function ran, for which key, whether it was served from the cache, and when the function itself ran:

- `ocache.get`: one event per cached call, from the key lookup until the call settles.
- `ocache.resolve`: one event per run of the cached function, in the foreground or in the background.

While nothing subscribes, a call takes the same path as with tracing off and builds no context object. Runtimes without `process.getBuiltinModule` or without tracing channels skip tracing entirely.

Tracing is on by default. Set `tracing: false` on a cached function or handler to keep its keys and values away from subscribers. Changing the option does not invalidate existing entries.

```ts
import { defineCachedFunction } from "ocache";

const getSecret = defineCachedFunction(fetchSecret, { maxAge: 60, tracing: false });
```

## Subscribing

Both channels are [`TracingChannel`](https://nodejs.org/api/diagnostics_channel.html#class-tracingchannel)s: `start` and `end` around the synchronous part of the call, `asyncStart` and `asyncEnd` when it settles, and `error` when it rejects, all with the same context object.

```ts
import { tracingChannel } from "node:diagnostics_channel";
import { GET_CHANNEL, RESOLVE_CHANNEL } from "ocache";
import type { CacheResolveTraceContext, CacheTraceContext } from "ocache";

tracingChannel<CacheTraceContext>(GET_CHANNEL).subscribe({
  start: (ctx) => {
    // `start` runs in the caller's async context, so a span started here gets the right parent.
  },
  asyncEnd: (ctx) => {
    console.log(`${ctx.group}:${ctx.name} ${ctx.key} -> ${ctx.status}`);
  },
  error: (ctx) => {
    console.error(`${ctx.name} failed:`, ctx.error);
  },
});

tracingChannel<CacheResolveTraceContext>(RESOLVE_CHANNEL).subscribe({
  asyncEnd: (ctx) => {
    console.log(`${ctx.name} ${ctx.key} ran (${ctx.status})`);
  },
});
```

## `ocache.get`

The event spans the whole call: the storage read, and on a `"miss"` or `"revalidated"` the run of the function it waits for. Subtract the nested `ocache.resolve` event to get the lookup alone.

| Field    | Description                                                                                                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `type`   | `"function"` or `"handler"`, which decides the shape of `result`                                                                                                                                       |
| `name`   | Resolved cache name                                                                                                                                                                                    |
| `group`  | Cache key group: `"functions"` or `"handlers"` unless set                                                                                                                                              |
| `event`  | The request event, when the first argument is one (cached handlers)                                                                                                                                    |
| `key`    | Cache key from `getKey`                                                                                                                                                                                |
| `keys`   | Full storage keys, one per `base` prefix in read order                                                                                                                                                 |
| `status` | `"hit"`, `"stale"`, `"revalidated"` or `"miss"`                                                                                                                                                        |
| `maxAge` | Fresh lifetime of the served value in seconds: the stored entry's for `"hit"` and `"stale"`, the new value's for `"miss"` and `"revalidated"`                                                          |
| `mtime`  | Write time of the served value in Unix milliseconds; `Date.now() - mtime` is its age                                                                                                                   |
| `result` | For a `"function"`, the value returned to the caller. For a `"handler"`, the `ResponseCacheEntry` (`status`, `headers`, `body`) the response is built from, including the `cacheStatusHeader` when set |
| `error`  | Error the call rejected with                                                                                                                                                                           |

`CacheTraceContext` is a union on `type`: checking `ctx.type === "handler"` narrows `result` to `ResponseCacheEntry` and makes `event` required.

`key`, `status`, `maxAge` and `mtime` are filled in during the call, so read them at `asyncEnd` or `error`. `status` is the same value `transform` receives on `entry.status`. Function arguments are not published, but `result` is: it is whatever the call returns.

Read request data from `event` at `start`. On a miss a cached handler narrows `event.req` to the headers its key covers before the handler runs, so by `asyncEnd` headers such as `traceparent` are gone; a hit never narrows it.

Concurrent misses for one key share a single run of the function. Each publishes its own `ocache.get` event with that run's `mtime`, and only the call that started the run publishes `ocache.resolve`. A `"stale"` call that joins a run in progress is served, and reports, the stored entry.

With `stream: true`, the `ocache.get` event of the request that fills the entry ends when the fill finishes, after its `Response` has been returned.

A cached handler that cannot store a response still serves it live: a body over `maxBodySize`, or a handler that reads `event.req` in a way narrowing forbids. Both `ocache.get` and `ocache.resolve` publish `error` for these, with `status: "miss"`, while the request answers normally.

## `ocache.resolve`

| Field    | Description                                                                                                                                                                |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`   | `"function"` or `"handler"`, which decides the shape of `result`                                                                                                           |
| `name`   | Resolved cache name                                                                                                                                                        |
| `group`  | Cache key group                                                                                                                                                            |
| `event`  | The request event, when the first argument is one                                                                                                                          |
| `key`    | Cache key from `getKey`                                                                                                                                                    |
| `status` | Status of the read that started the run: `"miss"`, `"revalidated"`, or `"stale"` for a background run                                                                      |
| `result` | The new entry before storage: `value` (a `ResponseCacheEntry` for a handler), `mtime`, and the `maxAge` and `staleMaxAge` `getMaxAge` gave (unset means the options apply) |
| `error`  | Error the function or `serialize` rejected with (`getMaxAge` errors go to `onError`)                                                                                       |

The event covers the function, `getMaxAge` and `serialize`; for a cached handler that includes reading the response body, and `result.mtime` is stamped after it, as the stored entry is. It ends before the storage write. A `maxResolveTime` timeout rejects the `ocache.get` event while the run keeps going, so the `ocache.resolve` event still ends when the function does.

## Bypassed calls

A call that skips the cache publishes nothing on either channel: `shouldBypassCache` on a cached function, and on a cached handler a non-cacheable method, a `Range` request, `shouldBypassCache`, or `headersOnly`.

## Background revalidation

A `"stale"` call returns the stored value right away and its refresh keeps running through `waitUntil`, so the `ocache.get` event ends before the refresh does. The refresh publishes its own `ocache.resolve` event with `status: "stale"`. It starts inside the caller's async context, so a span it opens gets the `ocache.get` span as its parent, even though it ends after it.
