# Tracing

With the `tracing` option, ocache publishes every cached call on the `ocache.get` [`node:diagnostics_channel`](https://nodejs.org/api/diagnostics_channel.html) tracing channel, so an APM tool or a metrics library can see which cached function ran, for which key, and whether it was served from the cache.

```ts
import { defineCachedFunction } from "ocache";

const getUser = defineCachedFunction(fetchUser, { maxAge: 60, tracing: true });
```

Cached handlers take the same option. Enabling it does not invalidate existing entries.

While nothing subscribes, a traced call takes the same path as an untraced one and builds no context object. Runtimes without `process.getBuiltinModule` or without tracing channels skip tracing entirely.

## Subscribing

`ocache.get` is a [`TracingChannel`](https://nodejs.org/api/diagnostics_channel.html#class-tracingchannel): `start` and `end` around the synchronous part of the call, `asyncStart` and `asyncEnd` when it settles, and `error` when it rejects, all with the same context object.

```ts
import { tracingChannel } from "node:diagnostics_channel";
import { GET_CHANNEL, type CacheTraceContext } from "ocache";

tracingChannel<object, CacheTraceContext>(GET_CHANNEL).subscribe({
  start: (ctx) => {
    // `start` runs in the caller's async context, so a span started here gets the right parent.
  },
  asyncEnd: (ctx) => {
    console.log(`${ctx.group}:${ctx.name} ${ctx.key} -> ${ctx.status}`);
  },
  error: (ctx) => {
    console.error(`${ctx.name} failed:`, ctx.error);
  },
});
```

## Context

| Field    | Description                                                                                                                                                       |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`   | `"function"` or `"handler"`, which decides the shape of `result`                                                                                                  |
| `name`   | Resolved cache name                                                                                                                                               |
| `group`  | Cache key group: `"functions"` or `"handlers"` unless set                                                                                                         |
| `event`  | The request event, when the first argument is one (cached handlers)                                                                                               |
| `key`    | Cache key from `getKey`, set before the storage read. Unset for a bypassed call                                                                                   |
| `status` | `"hit"`, `"stale"`, `"revalidated"` or `"miss"`, or `"bypass"` when `shouldBypassCache` skipped it                                                                |
| `result` | For a `"function"`, the value returned to the caller. For a `"handler"`, the stored `ResponseCacheEntry` (`status`, `headers`, `body`) the response is built from |
| `error`  | Error the call rejected with                                                                                                                                      |

`CacheTraceContext` is a union on `type`: checking `ctx.type === "handler"` narrows `result` to `ResponseCacheEntry` and makes `event` required.

`key` and `status` are filled in during the call, so read them at `asyncEnd` or `error`. `status` is the same value `transform` receives on `entry.status`. Function arguments are not published.

A cached handler only publishes for requests that reach the cache. A request it sends straight to the handler (a non-cacheable method, a `Range` request, `shouldBypassCache`, or `headersOnly`) is not traced.

## Background revalidation

A `"stale"` call returns the stored value right away and its refresh keeps running through `waitUntil`, so the `ocache.get` event ends before the refresh does. The refresh still starts inside the caller's async context, so whatever it does is still attributed to the same trace.
