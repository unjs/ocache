# Caching HTTP Handlers

Wrap an HTTP handler with `defineCachedHandler` to cache its `Response` automatically. It supports `etag` and `304 Not Modified`. It works with any runtime that provides the standard `Request` and `Response` APIs. The event has the form `{ req: Request; url?: URL }`.

```ts
import { defineCachedHandler } from "ocache";

const handler = defineCachedHandler(
  async (event) => {
    const url = event.url ?? new URL(event.req.url);
    const product = await db.getProduct(url.pathname.split("/").pop());
    return Response.json(product);
  },
  {
    maxAge: 300, // cache fresh for 5 minutes
    swr: true, // serve stale while revalidating in the background
    staleMaxAge: 600, // ...for up to 10 minutes past expiry
  },
);

// Call it with any { req, url? } event
const res = await handler({ req: new Request("https://example.com/p/42") });
```

The first request runs your handler and stores the response. Later requests use the cache until the entry expires.

> [!NOTE]
> `maxAge` defaults to `1` second. Set it explicitly for anything you actually want cached.

## What it does

- **Cache keys** — ocache creates keys from the handler [name](#cache-key-name), request [origin](#multi-host-deployments), URL path, and request method. The keys also include query parameters and headers that you choose to vary.
- **Conditional requests** — ocache responds with `304 Not Modified` when the client sends a matching `if-none-match` or `if-modified-since`.
- **Response headers** — ocache creates `etag` and `cache-control` when the handler does not set them. It never creates `last-modified`, because the time it fills an entry is not the time the content changed. Set that header yourself when the handler knows the real modification time.
- **`Vary`** — ocache advertises the request headers that vary the response. These come from `varies` and include `Cookie` when you set `allowCookies`. ocache refuses to store a response if its own `Vary` names another header.
- **Binary responses** — ocache caches images, tiles, and other non-text bodies. It replays them byte for byte.
- **Resolution deadline** — a handler or upstream that never responds cannot block its cache key forever. ocache abandons the shared resolution after [`maxResolveTime`](#resolution-deadline), which is 30 seconds by default. Waiting requests reject instead of continuing to wait, and the handler's request is aborted.

## Cacheable requests

ocache caches only `GET` and `HEAD` requests. All other methods, such as `POST`, `PUT`, and `DELETE`, bypass the cache and reach the handler unchanged.

A request with a `Range` header also bypasses the cache, for any method. A range request asks for a _part_ of a resource. Its response is valid only for the request that specified that range. If ocache stored it under a key without the range, all callers could receive one caller's partial response. It would also buffer a partial body without benefit. Your handler processes range requests without changes from ocache.

```ts
const handler = defineCachedHandler(myHandler, { maxAge: 60 });

await handler({ req: new Request(url) }); // GET  → cached
await handler({ req: new Request(url, { method: "POST", body }) }); // POST → runs the handler, body intact
```

> [!IMPORTANT]
> A bypassed response passes through exactly as the handler returned it. ocache does not buffer the body, so streaming bodies continue to work. It does not create cache headers or an incorrect `304`.

ocache caches `GET` and `HEAD` **separately**. A `HEAD` response is a different representation because a compliant framework removes its body. If both methods shared one entry, a `HEAD` request could store a response without a body. Later `GET` requests would then receive that empty response. Each method requires its own handler call for each resource and TTL. This prevents blank pages.

> [!NOTE]
> The method remains part of the key when you provide a custom `getKey`. Your key identifies _which content_ to cache. ocache adds the `GET` and `HEAD` separation. `GET` keys have no method component, so they do not change.

Use `shouldBypassCache` to bypass more requests. ocache combines it with the built-in checks using OR. It can only bypass _more_ requests. It cannot force ocache to cache another method or a range request:

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  // Skip the cache for logged-in users
  shouldBypassCache: (event) => event.req.headers.has("authorization"),
});
```

A request excluded this way behaves like a `POST`. It reaches the handler **unchanged**, including its `Authorization` header, cookies, and full query string. Therefore, `shouldBypassCache` is an alternative to [`allowAuthorization`](#credential-headers). The handler can read the credential because ocache never stores or shares the response.

## Cache key name

Every key contains a `name`. ocache resolves it in the same way as the name of a [cached function](/functions#cache-keys): `opts.name || handler.name || anon_<hash(handler)>`. The name prevents two handlers from colliding when they share one `storage` and use the same path.

```ts
const storage = createMemoryStorage();

// Named handlers → "/cache:handlers:dashboard:..." and "/cache:handlers:profile:..."
const dashboard = defineCachedHandler(
  async function dashboard(event) {
    return renderDashboard(event);
  },
  { maxAge: 60, storage },
);
const profile = defineCachedHandler(
  async function profile(event) {
    return renderProfile(event);
  },
  { maxAge: 60, storage },
);
```

> [!IMPORTANT]
> The fallback hashes the handler **source**. Handlers from the same factory have identical source but can have different closed-over variables. These handlers share a name. If they also share `storage`, they share entries. One tenant can then receive another tenant's cached response. Pass an explicit `name` or `getKey` when you build handlers in a loop or factory.
>
> ```ts
> // ✗ both handlers key identically
> const make = (tenant) => defineCachedHandler(() => render(tenant), { maxAge: 60, storage });
> // ✓ named per instance
> const make = (tenant) =>
>   defineCachedHandler(() => render(tenant), { maxAge: 60, name: `page-${tenant}`, storage });
> ```

ocache derives the name from the handler. The source hash stays stable across restarts, so you can use the keys with a persistent backend.

## Multi-host deployments

The request **origin** is part of the automatically generated key. The origin includes the scheme, host, and port. Therefore, one handler that serves several hostnames stores a separate entry for each host. This is common in a virtual host setup. `https://a.example/home` and `https://b.example/home` never share a cached rendering. Different schemes or ports also use separate entries.

The origin comes from `event.url`, or from `new URL(event.req.url)` when `event.url` is not available. It is the value that your adapter resolved, not the raw `Host` request header. Some adapters build the URL _from_ `Host`, so these values match. A reverse proxy before your app must still be trusted to normalize `Host` and `X-Forwarded-Host`.

Because only the resolved origin is in the key, ocache also **rewrites the `Host` header** that your handler reads to the host of that origin. A handler that builds a canonical link or an absolute URL from `Host` therefore builds it from a value the key covers, on every adapter. Declare `varies: ["host"]` if you need the raw header instead; the value then becomes part of the key and appears in `Vary`.

> [!NOTE]
> A custom [`getKey`](/query-params#edge-cases) replaces the full automatic key, including the origin. If your handler renders host-dependent content, add the origin to your key. Examples include canonical links, absolute asset URLs, and `Location`.

## Varying by request headers

By default, the cache key depends only on the request origin and URL path. All clients on the same host share one cached entry. List header names in `varies` to cache a separate variant for each header value:

```ts
const handler = defineCachedHandler(
  async (event) => {
    const lang = event.req.headers.get("accept-language") ?? "en";
    return new Response(renderPage(lang), {
      headers: { "content-type": "text/html" },
    });
  },
  {
    maxAge: 300,
    varies: ["accept-language"], // one cached entry per language
  },
);
```

ocache also adds these header names to the response `Vary` header. It removes duplicates without regard to case. It does not change a `Vary: *` set by the handler. As a result, downstream caches and CDNs also store each variant separately. [`allowCookies`](/cookies) also adds `Cookie` to `Vary`. The cache key uses only the allowed cookie subset, but the response still varies by the full header because `Vary` cannot describe a subset. [`allowQuery`](/query-params) adds nothing to `Vary`. Query parameters are in the URL, and downstream caches already include the URL in their keys.

> [!IMPORTANT]
> **A `Vary` set by your handler must name only headers that ocache varies on.** `Vary: Accept-Language` correctly states that responses for different languages are not interchangeable. However, ocache keys only on `varies` and on `Cookie` when you set `allowCookies`. It **does not store** a response that names another header. It also does not synthesize `Cache-Control` for that response. Otherwise, ocache could replay the first language to all other languages. The response would still contain `Vary`, which downstream caches would trust. Add the header to `varies` to cache the response correctly:
>
> ```ts
> defineCachedHandler(
>   (event) =>
>     new Response(renderPage(event.req.headers.get("accept-language")), {
>       headers: { vary: "Accept-Language" }, // ocache merges/dedups its own copy in
>     }),
>   { maxAge: 300, varies: ["accept-language"] }, // ...and keys on it, so this caches
> );
> ```

> [!TIP]
> **The handler can read varying headers.** Their values are part of the cache key, so each distinct value gets its own entry. It is safe to render content from them. This also applies to credential headers. Listing `cookie` or `authorization` in `varies` is a broad opt-in. ocache keys on the raw header and forwards it to the handler. ocache removes these headers only when you do _not_ list them. See [Cookies](/cookies) and the next section.

## Headers the handler can't see

**For cacheable requests, a handler can read only the headers that the cache key covers.** ocache removes all other request headers before it runs the handler. For a removed header, `event.req.headers.get(...)` returns `null`.

```ts
defineCachedHandler(
  (event) => {
    const tenant = event.req.headers.get("x-api-key"); // null — not in `varies`
    return Response.json(loadTenant(tenant));
  },
  { maxAge: 300 },
);
```

This prevents a handler from rendering content from an input that the key does not distinguish. Without this rule, ocache could store the first caller's tenant page under a shared key. It could advertise the page to browsers and CDNs with a synthesized `max-age` and no `Vary`. It could then replay the page to everyone else for the rest of the TTL. The same risk applies to `Accept`, `Accept-Language`, and `Origin` when it is copied into a CORS header. It also applies to `X-Forwarded-Host` and `X-Forwarded-Proto`. Behind a proxy, the host in the cache key can be the internal host. If a forwarded host reached the handler, both tenants could use one entry.

You can use either of these fixes:

- **`varies: ["x-api-key"]`** — the header becomes part of the entry key and reaches the handler. ocache also advertises it in the response `Vary`. Each distinct value gets one entry.
- **[`shouldBypassCache`](#cacheable-requests)** — keep these requests out of the cache. A bypassed request reaches the handler unchanged.

There are **no exemptions**. Every header that the key does not cover is removed, including `If-None-Match`, `If-Modified-Since`, and the trace headers `traceparent`, `tracestate`, `X-Request-Id`, and `X-Correlation-Id`. `Host` is the one rewritten name: it stays visible, but with the [resolved origin's host](#multi-host-deployments) as its value rather than the raw one, which is the value the key covers. `User-Agent` is not exempt either. Output for different devices or bots needs separate keys, so add `User-Agent` to `varies` if you render from it.

> [!WARNING]
> The rule is one-directional for a reason: a value the key does not cover must never reach your response. If a handler renders such a value into a cacheable `200`, ocache stores one caller's value and serves it to every later caller for the full lifetime. Removing the header makes that impossible rather than trusting the handler not to do it.

ocache still answers conditional requests itself — see [Conditional requests & 304](#conditional-requests--304). It reads the validators from the original request before narrowing, so removing them from the handler's view does not disable `304` responses. Your handler cannot do its own conditional handling, and code that propagates trace context must read it from your framework's event or middleware, which ocache never touches.

> [!NOTE]
> ocache narrows only cacheable (`GET` and `HEAD`) requests. It narrows only the request that the handler receives. Your middleware, framework, and runtime still receive the original request.

> [!NOTE]
> Narrowing replaces `event.req`, and `event.url` when [`allowQuery`](/query-params) applies. If your framework exposes either as read-only, ocache cannot narrow the request. It then reports the error through `onError` and serves that request as a bypass: the handler receives the original request, and the response is neither stored nor given cache headers.

## Credential headers

This rule is especially important for `Authorization` and `Proxy-Authorization`. These headers **do not participate in caching by default**. For cacheable (`GET` and `HEAD`) requests, ocache removes both headers before the handler runs. It treats them like a cookie that is not in [`allowCookies`](/cookies). Therefore, a handler cannot render per-user content from a credential that is missing from the cache key. This prevents storage under a shared anonymous key.

If your handler needs the credential, opt in with `allowAuthorization`:

```ts
const handler = defineCachedHandler(
  async (event) => {
    const token = event.req.headers.get("authorization");
    return Response.json(await loadDashboard(token));
  },
  {
    maxAge: 60,
    allowAuthorization: true, // keyed per credential, advertised in `Vary`, visible to the handler
  },
);
```

This opt-in adds both header names to `varies`. They vary the cache key and reach the handler. ocache also adds them to the response `Vary` header. Listing `authorization` in `varies` has the same effect.

> [!CAUTION]
> **`allowAuthorization` caches one entry for each credential value. All clients that send that value share the entry.** ocache combines concurrent requests with the same token into one handler call. It replays the stored response to later requests. Use this option only when this behavior is correct. A token that maps to more than one user view still needs a user-specific `getKey`. A token that rotates also needs one.
>
> When the response is per-user and shouldn't be shared at all, skip the cache for those requests instead:
>
> ```ts
> defineCachedHandler(myHandler, {
>   maxAge: 60,
>   shouldBypassCache: (event) => event.req.headers.has("authorization"),
> });
> ```

This affects only cacheable requests. Other methods, such as `POST`, bypass the cache. Requests excluded by `shouldBypassCache` also bypass it. These requests reach the handler with their credentials unchanged.

## Conditional requests & 304

The handler returns `304 Not Modified` with an empty body when `if-none-match` matches the stored `etag`. When the request has no `if-none-match`, it returns 304 if `if-modified-since` is at or after the `last-modified` **that the handler set**. ocache never creates that header, so a handler that sets no date is validated by its `etag` alone:

```ts
const handler = defineCachedHandler(() => new Response("<h1>Hi</h1>"), {
  maxAge: 300,
});

const first = await handler({ req: new Request(url) });
const etag = first.headers.get("etag");

// Browser revalidates with the etag it received
const second = await handler({
  req: new Request(url, { headers: { "if-none-match": etag } }),
});
second.status; // 304
```

`if-none-match` takes precedence: when a request sends both headers and its etag does not match, ocache serves the full response and ignores `if-modified-since`. Browsers send both together, so the date alone must never claim an outdated representation is current.

ocache owns this decision alone. It captures `if-none-match` and `if-modified-since` from the original request before [narrowing](#what-the-handler-sees) removes them, so **your handler never sees them**. A handler that used to serve its own `304` — a `serveStatic`-style route, or one forwarding validators to an upstream — now always renders the full representation, and ocache decides the `304` from the stored `etag`. Put a validator in `varies` if the handler must read it, at the cost of one entry per distinct value; `shouldBypassCache` is usually the better choice.

The header accepts a list of etags, and it matches any of them. Comparison is weak, so `W/"abc"` matches `"abc"`. The value `*` always matches a cached response.

The `304` repeats the headers that describe the representation it stands in for: `cache-control`, `content-location`, `date`, `etag`, `expires`, `last-modified`, and `vary`. The validators let the client update the response it already holds, the policy headers refresh its freshness lifetime so it does not revalidate on every later request, and `vary` lets downstream caches keep the variant dimension. The cache status header is included too, since a `HIT` answered as `304` is still a `HIT`.

## Headers-only mode

Set `headersOnly: true` to answer conditional requests **without** caching the response body. Your handler always runs, because nothing is stored: ocache compares the request conditions against the `etag` and `last-modified` of the response your handler just produced. When one matches, it returns a `304` with no body instead of that response. Otherwise it returns the response unchanged. It never stores the response:

```ts
const handler = defineCachedHandler(myHandler, {
  headersOnly: true,
  maxAge: 60,
});
```

Use this option when the handler already creates its own `etag` and `last-modified`. Without those headers, no condition can match and every request gets the full response, because ocache never buffers the body to mint validators here. It saves the response transfer, not the handler run, and only for `GET` and `HEAD` responses with a cacheable status (`200`, `203`, `301`, `308`). A custom `handleCacheHeaders` receives the same validators and can decide differently.

## Cache-status header

By default, ocache adds a CDN-style `X-Cache` header. It reports how ocache served the response: `MISS`, `HIT`, `STALE`, or `REVALIDATED`.

```ts
defineCachedHandler(myHandler, { maxAge: 60 }); // adds X-Cache
defineCachedHandler(myHandler, { maxAge: 60, cacheStatusHeader: "x-my-cache" }); // custom name
defineCachedHandler(myHandler, { maxAge: 60, cacheStatusHeader: false }); // disable
```

## Response size

ocache buffers a response body to store it. A body it can never store is not worth buffering, so it stops reading one that grows past `maxBodySize` bytes:

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  maxBodySize: 5 * 1024 * 1024, // never buffer more than 5 MB
});
```

Without the option, the limit comes from your storage backend. [Memory storage](/storage#memory-storage--lru) declares its `maxBytes` ceiling, and ocache derives the largest body that could fit inside one entry: **`maxBytes / (8 / 3)`**, or about **39 MB** under the 100 MB default. The `8 / 3` covers the worst-case cost of a stored body, since a binary body is base64-encoded and a string costs 2 bytes per character. A backend that declares no ceiling, such as a Redis or filesystem adapter, sets no limit: pass `maxBodySize` yourself there. Set it to `Infinity` or `0` to buffer every response the backend accepts.

A larger response is **still served, in full**. It streams straight through to the client, exactly as a [bypassed request](#cacheable-requests) does: ocache stores nothing, adds no `X-Cache`, and synthesizes no `etag` or `Cache-Control` for it. Every request for that resource runs the handler.

> [!NOTE]
> Concurrent requests for one key normally share a single resolution, but a live stream can only be read once. The request whose handler produced the oversized body receives it; the requests that joined it run the handler again for their own response.

> [!IMPORTANT]
> This limit exists because your process buffers the whole body before the storage ceiling can refuse the entry. Set it on any route that proxies upstream responses whose size you do not control.

## Resolution deadline

A handler that never responds cannot hold its cache key forever. ocache abandons the shared resolution after `maxResolveTime` seconds, which is **30** by default, and every waiting request rejects with a `TimeoutError`. The [functions guide](/functions#resolution-deadline) describes the setting in full.

A handler also receives the deadline as an `AbortSignal` on `event.req.signal`. Pass it to the work you start, and a timed-out resolution releases its upstream connection instead of running on unwatched:

```ts
export default defineCachedHandler(
  async (event) => {
    const res = await fetch("https://slow.example/report", {
      signal: event.req.signal, // aborted if this resolution hits its deadline
    });
    return new Response(await res.text());
  },
  { maxAge: 300, maxResolveTime: 5 },
);
```

The abort reason is the same `TimeoutError` the waiting requests receive, so `fetch` rejects with it.

> [!IMPORTANT]
> This is **not** the client's signal. ocache serves concurrent requests for one key from a single shared resolution, so a client that disconnects does not cancel the handler: other requests are still waiting for that same work, and a background SWR refresh has no client at all. Only the deadline aborts the signal. Setting `maxResolveTime` to `0` or `Infinity` leaves a signal that never aborts.

## Framework integration hooks

Override any of these hooks to support the request and response types of a specific framework:

- `toResponse(value, event)` — converts the handler return value to a `Response`. By default, it returns an existing `Response` unchanged. For other values, it returns `new Response(String(value))`.
- `createResponse(body, init)` — builds the final `Response` served from the cache. `body` is a `string` for text, a `Uint8Array` for binary data, or `null` for an empty response or `304`. The default is `new Response(body, init)`.
- `handleCacheHeaders(event, conditions)` — decides whether to respond with a `304`. Return `true` to respond immediately. The default uses the built-in `if-none-match` and `if-modified-since` check. Read the request validators from `conditions.ifNoneMatch` and `conditions.ifModifiedSince`, **not** from `event.req`: narrowing has already removed them by the time this hook runs.

```ts
const handler = defineCachedHandler(
  // Handler returns a plain object...
  async (event) => ({ id: 42, name: "Widget" }),
  {
    maxAge: 300,
    // ...toResponse turns it into JSON
    toResponse: (value) => Response.json(value),
  },
);
```

## On-demand revalidation

The returned handler provides `.expire(event)`, `.invalidate(event)`, and `.resolveKeys(event)`. These methods match the methods on a [cached function](/invalidation). Each method takes a request `event` and gets the exact key that the handler used:

```ts
await page.expire(event); // mark stale — serve stale once more, refresh in background (SWR)
await page.invalidate(event); // remove — next request blocks on a fresh render
```

These methods target the **resource**, not only the method in the event. They purge or expire both the `GET` and `HEAD` entries for that URL. No entry remains that advertises the old `etag`. `.resolveKeys(event)` returns the same set. It returns one key for each `base` prefix and method variant, with the event key first.

> [!NOTE]
> The standalone `invalidateCache()` and `expireCache()` helpers cannot see the request method. They target only the variant implied by their arguments. For cached handlers, use the handler methods when possible.

See [ISR → on-demand revalidation](/isr#on-demand-revalidation) for the full recipe.
