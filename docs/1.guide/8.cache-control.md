# Cache-Control & Eligibility

`defineCachedHandler` synthesizes a `Cache-Control` header for cacheable responses, but it always defers to what the handler sets and to a set of built-in eligibility rules. This page covers how to keep responses out of the cache, decouple server-side storage from client caching, and add your own eligibility rules.

## What is never cached

Before storing a response, ocache applies these built-in checks. A response failing **any** of them is still returned to the caller, but is never stored or served from the cache:

- **Any status outside `200`, `203`, `301`, `308`** — the storable statuses are an explicit allowlist, not "anything that isn't an error". Those four are the ones whose response is a complete, reusable representation of what was requested. Everything else is refused, including `4xx`/`5xx` (an error is not a representation), `201`/`202`/`300` (the outcome of an operation, or an unresolved choice), `204`/`205`/`304` (nothing to replay — a `304` in particular answers one client's conditional request), `206` (a partial body, valid only for the range that was asked for) and the temporary redirects `302`/`303`/`307` (a per-request answer: an auth redirect to `/login` stored under an anonymous key would be served to everyone else hitting that URL).
- **A `Cache-Control` opt-out from the handler** — `no-store`, `private`, `no-cache`, or a zero **shared** lifetime (`s-maxage` when present, `max-age` otherwise). See [Private / non-cacheable responses](#private--non-cacheable-responses).
- **`Vary: *`** — the strongest "do not share this" signal short of `no-store`: no stored response may ever match such a request (RFC 9111 §4.1). ocache keeps one entry per cache key, so the only honest handling is to refuse the entry.
- **A `Vary` naming a request header ocache does not key on** — declaring `Vary` is how a handler says "this response is not interchangeable" (RFC 9111 §4.1). ocache keys on [`varies`](/guide/handler#varying-by-request-headers) (plus `Cookie` under [`allowCookies`](/guide/cookies)) and nothing else, so a handler returning `Vary: Accept-Language` without a matching `varies: ["accept-language"]` would have its first rendering replayed to every other language. The entry is refused instead. A `Vary` that only names headers ocache already varies on caches normally, so the fix is to make the two agree — see [Varying by request headers](/guide/handler#varying-by-request-headers).
- **Empty body** — nothing to replay.
- **Missing `etag` / `last-modified`** — required for conditional requests (ocache adds these itself when the handler omits them, so this mainly guards handler-set placeholder values).

These checks always apply and cannot be turned off.

One more rule sits alongside them and _is_ configurable: a response body over [`maxBodySize`](/guide/handler#large-responses) (5 MB by default) is streamed through to the caller and never cached. Unlike the checks above it says nothing about eligibility — such a response is perfectly cacheable, it just costs more to buffer than the ceiling allows.

A response the built-in checks refuse also gets **no synthesized `Cache-Control`** — with one deliberate exception, `shouldCache`, below. A `500` is returned to the caller with no synthesized `Cache-Control` at all, so a shared cache in front of your handler doesn't pin the error for `maxAge + staleMaxAge` while ocache re-runs the handler on every request; the same goes for a response refused over its `Vary` (`*` or an unkeyed header), which is the case that needs it most — those carry no `Cache-Control` of their own, so nothing else would have suppressed the advertisement. The `Cache-Control` opt-outs need no special handling here: they _are_ a `Cache-Control` the handler set, and ocache never overwrites one (whatever the status), so its directive is what reaches the client.

The exception is [`shouldCache`](#custom-eligibility-shouldcache): a response your own hook rejects is still advertised with the synthesized lifetime. That is on purpose — "ocache doesn't keep this, but a CDN may" is a legitimate setup, and `sendCacheControl: false` is its inverse ("ocache keeps this, but nobody downstream may"). Reach for that one, or set a `Cache-Control` on the response, if you want the advertisement to go away too.

## Private / non-cacheable responses

To keep a specific response out of the cache from inside the handler, set a `Cache-Control` that says so. All of these are honored — the response is returned to the caller with its header intact, but never stored and never served from the cache:

| Directive                  | Meaning                                        |
| -------------------------- | ---------------------------------------------- |
| `no-store`                 | Never store this anywhere.                     |
| `private`                  | Not in a shared cache — and ocache is one.     |
| `no-cache`                 | Must not be reused without revalidating first. |
| `max-age=0` / `s-maxage=0` | Stale the moment it was produced.              |

Directives are parsed properly, not substring-matched: `max-age=0600` is 600 seconds, and a `0` in some other directive's value (`stale-while-revalidate=0`) is not a zero lifetime.

`s-maxage` overrides `max-age` for shared caches (RFC 9111 §5.2.2.10), and ocache is one — so when both are set, only `s-maxage` decides. `public, max-age=0, s-maxage=600` ("browsers revalidate, shared caches keep it for 10 minutes") is cached for 600 seconds, and `public, s-maxage=0, max-age=600` is not cached at all.

> [!NOTE]
> The same rule applies to the header ocache synthesizes for itself: configuring `maxAge: 0` advertises a zero lifetime (`max-age=0`, or `s-maxage=0` under `swr`) and therefore stores nothing. That is what a zero lifetime means — such an entry would be expired the moment it was written, so the handler runs on every request either way. An option you leave out — or pass as an explicit `undefined` — takes its default (`maxAge: 1`) instead, so only a lifetime you actually write as `0` opts out.

```ts
const handler = defineCachedHandler(
  async (event) => {
    const user = await getUser(event);
    if (!user) {
      return new Response("Please log in", { status: 401 });
    }
    // Personalized — never cache this one
    return new Response(renderDashboard(user), {
      headers: {
        "content-type": "text/html",
        "cache-control": "private",
      },
    });
  },
  { maxAge: 300 },
);
```

Any **other** `Cache-Control` the handler sets is preserved verbatim — ocache only synthesizes `max-age` / `s-maxage` / `stale-while-revalidate` when the handler didn't set a `Cache-Control` of its own.

> [!IMPORTANT]
> An opt-out only controls what gets **stored** — it does not partition the cache key. Concurrent requests are still coalesced by cache key, so responses that differ per user must be keyed correctly (via [`varies`](/guide/handler) or [`allowCookies`](/guide/cookies)) or a personalized body could be shared.

> [!NOTE]
> `no-cache` is currently rejected outright rather than stored-and-always-revalidated. RFC 9111 §5.2.2.4 permits storing such a response as long as it is revalidated with the origin before every reuse; ocache has no foreground-revalidation path today, so "stored but always revalidated" would buy nothing over not storing.

## Never serve this stale (`must-revalidate`)

`must-revalidate` is **not** an opt-out: it constrains stale serving, not storage. A response carrying it is stored and served from cache normally while it is fresh — but it is never served stale, even with `swr: true` and a wide `staleMaxAge`. Once the entry expires, the next request revalidates in the **foreground** and waits for the fresh response:

```ts
const handler = defineCachedHandler(
  async () => {
    return new Response(await renderPrices(), {
      headers: { "cache-control": "public, max-age=60, must-revalidate" },
    });
  },
  { maxAge: 60, swr: true, staleMaxAge: 600 }, // SWR everywhere else, never for this response
);
```

Internally this is a per-entry `staleMaxAge: 0` — the same mechanism [`getMaxAge`](/guide/api) uses to give one entry its own lifetime — so it applies to that response only, not to the whole handler.

## Server-only caching (`sendCacheControl`)

Sometimes you want to cache a response **in your own storage** (to save recomputing it) while telling browsers and CDNs _not_ to cache it — for example a page that is expensive to build but must always be revalidated downstream. Reaching for `no-store` / `private` doesn't work here: those (and every other opt-out above) also disqualify the response from storage.

Set `sendCacheControl: false` to decouple the two. The response is still stored and served from cache (SWR, `etag`, and `last-modified` all still apply), but no `Cache-Control` header is emitted:

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  swr: true,
  sendCacheControl: false, // stored & served from cache, but nothing advertised downstream
});
```

This only governs ocache's own synthesis — a `Cache-Control` the handler sets explicitly is still preserved and sent. `Vary` is likewise unaffected: it describes the response, not a caching directive.

It is also the answer when [`allowCookies`](/guide/cookies) has tanked your CDN hit rate. A cookie-keyed route emits `Vary: Cookie`, which downstream caches can barely use; `sendCacheControl: false` keeps the server-side cache and stops advertising a shared-cacheability that wasn't going to be usable anyway.

> [!TIP]
> If `invalidateCache`/`expireCache` clears your storage but callers still get stale responses, a browser or CDN in front of the handler is likely serving from its own copy, cached independently via the synthesized `Cache-Control` — a purge to server storage never reaches it. `sendCacheControl: false` avoids this by never letting the client/CDN cache the response in the first place.

## Custom eligibility (`shouldCache`)

Use `shouldCache` to add your own rejection rule on top of the built-in checks. It receives the serialized response and returns `false` to skip caching (the response is still returned to the caller). For example, to keep the permanent redirects (`301`/`308`) out of the cache too, which the built-in checks do allow:

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  shouldCache: (res) => res.status < 300,
});
```

Key behaviors:

- **ANDed with the built-ins.** `shouldCache` can only _narrow_ what gets cached — it can never force-cache a response the built-in checks reject.
- **May be async.** Return a `boolean` or a `Promise<boolean>`.
- **Runs on reads too.** It gates both storing a fresh response and serving a stored one (including the stale-while-revalidate serve decision), so keep it fast and decide only from the passed entry.
- **Fails closed.** A throwing hook is treated as non-cacheable and reported via `onError`.
