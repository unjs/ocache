# Caching HTTP Handlers

Wrap an HTTP handler with `defineCachedHandler` to cache its `Response` automatically, complete with `etag`, `last-modified`, and `304 Not Modified` support. It works with any runtime that has standard `Request`/`Response` — the event is just `{ req: Request; url?: URL }`.

```ts
import { defineCachedHandler } from "ocache";

const handler = defineCachedHandler(
  async (event) => {
    const url = event.url ?? new URL(event.req.url);
    const product = await db.getProduct(url.pathname.split("/").pop());
    return Response.json(product);
  },
  {
    maxAge: 300, // cache fresh for 5 minutes
    swr: true, // serve stale while revalidating in the background
    staleMaxAge: 600, // ...for up to 10 minutes past expiry
  },
);

// Call it with any { req, url? } event
const res = await handler({ req: new Request("https://example.com/p/42") });
```

The first request runs your handler and stores the response; subsequent requests are served from the cache until the entry expires.

> [!NOTE]
> `maxAge` defaults to `1` second. Set it explicitly for anything you actually want cached.

## What it does

- **Cache keys** — auto-generated from the handler's [name](#cache-key-name), the request [origin](#multi-host-deployments) and URL path (plus any query params and headers you opt into varying, see below) and the request method.
- **Conditional requests** — answers `304 Not Modified` when the client sends a matching `if-none-match` / `if-modified-since`.
- **Response headers** — synthesizes `etag`, `last-modified`, and `cache-control` when the handler didn't set them.
- **`Vary`** — advertises which request headers the response varies on (from `varies`, plus `Cookie` when `allowCookies` is set), and refuses to store a response whose own `Vary` names anything else.
- **Binary responses** — images, tiles, and other non-text bodies are cached and replayed byte-for-byte.
- **Resolution deadline** — a handler (or an upstream) that never responds can't wedge its cache key: the shared resolution is abandoned after [`maxResolveTime`](/guide/functions#resolution-deadline), 30 seconds by default, and the requests waiting on it reject instead of hanging.

## Cacheable requests

Only `GET` and `HEAD` requests are cached. Every other method (`POST`, `PUT`, `DELETE`, ...) bypasses the cache and reaches the handler untouched.

Requests carrying a `Range` header bypass too, whatever their method. A ranged request asks for a _slice_ of the resource, so its response is only valid for the request that named that range — caching it under the range-free key would replay one caller's truncation to everyone (and buffer a partial body for no benefit). Range handling is left entirely to your handler, unchanged.

```ts
const handler = defineCachedHandler(myHandler, { maxAge: 60 });

await handler({ req: new Request(url) }); // GET  → cached
await handler({ req: new Request(url, { method: "POST", body }) }); // POST → runs the handler, body intact
```

> [!IMPORTANT]
> A bypassed response passes through exactly as the handler returned it — no body buffering (streaming bodies survive), no synthesized cache headers, and no spurious `304`.

`GET` and `HEAD` are cached **separately**. A `HEAD` response is a different representation — a spec-compliant framework strips its body — so sharing one entry would let a single `HEAD` request seed the cache with a body-less response that every subsequent `GET` is then served. Each method costs its own handler call per resource per TTL; that is the price of not serving a blank page.

> [!NOTE]
> The method is part of the key even when you supply a custom `getKey`: your key expresses _which content_ is being cached, and ocache keeps the `GET`/`HEAD` split on top of it. `GET` keys carry no method component, so they are unchanged.

You can bypass additional requests with `shouldBypassCache`, which is ORed on top of the built-in checks (it can only bypass _more_ requests, never force-cache a non-`GET`/`HEAD` or ranged one):

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  // Skip the cache for logged-in users
  shouldBypassCache: (event) => event.req.headers.has("authorization"),
});
```

A request you exclude this way gets the same treatment as a `POST`: it reaches the handler **untouched**, with its `Authorization` header, its cookies and its full query string intact. That is what makes `shouldBypassCache` a usable alternative to [`allowAuthorization`](#credential-headers) — the handler can read the credential precisely because the response is never stored or shared.

## Cache key name

Every key carries a `name` component, resolved exactly like a [cached function's](/guide/functions#cache-keys): `opts.name || handler.name || anon_<hash(handler)>`. It is what keeps two handlers that share one `storage` and can see the same path from colliding.

```ts
const storage = createMemoryStorage();

// Named handlers → "/cache:handlers:dashboard:..." and "/cache:handlers:profile:..."
const dashboard = defineCachedHandler(
  async function dashboard(event) {
    return renderDashboard(event);
  },
  { maxAge: 60, storage },
);
const profile = defineCachedHandler(
  async function profile(event) {
    return renderProfile(event);
  },
  { maxAge: 60, storage },
);
```

> [!IMPORTANT]
> The fallback hashes the handler **source**, so handlers produced by the same factory — identical source, different closed-over variables — share a name. Sharing a `storage` then means sharing entries: one tenant's cached response is served to another. Pass an explicit `name` (or `getKey`) whenever you build handlers in a loop or a factory.
>
> ```ts
> // ✗ both handlers key identically
> const make = (tenant) => defineCachedHandler(() => render(tenant), { maxAge: 60, storage });
> // ✓ named per instance
> const make = (tenant) =>
>   defineCachedHandler(() => render(tenant), { maxAge: 60, name: `page-${tenant}`, storage });
> ```

The name is derived from the handler, so a source hash is stable across restarts — which is what makes keys usable with a persistent backend.

## Multi-host deployments

The request **origin** — scheme, host and port — is part of the auto-generated key, so one handler instance serving several hostnames (the usual vhost setup) stores a separate entry per host. `https://a.example/home` and `https://b.example/home` never share a cached rendering, and neither do `http://` vs `https://` or two ports.

The origin comes from `event.url` (falling back to `new URL(event.req.url)`) — what your adapter resolved — never from the raw `Host` request header. On adapters that build the URL _from_ `Host` the two coincide, so a reverse proxy in front of your app must still be trusted to normalize `Host` / `X-Forwarded-Host` as usual.

> [!NOTE]
> A custom [`getKey`](/guide/query-params#edge-cases) replaces the auto key entirely, origin included. If your handler renders anything host-dependent (canonical links, absolute asset URLs, `Location`), include the origin in the key yourself.

## Varying by request headers

By default the cache key depends only on the request origin and URL path — every client on the same host shares one cached entry. List header names in `varies` to cache a separate variant per header value:

```ts
const handler = defineCachedHandler(
  async (event) => {
    const lang = event.req.headers.get("accept-language") ?? "en";
    return new Response(renderPage(lang), {
      headers: { "content-type": "text/html" },
    });
  },
  {
    maxAge: 300,
    varies: ["accept-language"], // one cached entry per language
  },
);
```

The same header names are also merged into the response `Vary` header (case-insensitively deduped, and a handler-set `Vary: *` is left untouched) so downstream caches and CDNs store per-variant too. [`allowCookies`](/guide/cookies) contributes `Cookie` to that header as well — it keys on the allowlisted subset, but the response still varies by the header, and `Vary` can't say less. Note that [`allowQuery`](/guide/query-params) contributes nothing: query params live in the URL, which downstream caches already key on.

> [!IMPORTANT]
> **A `Vary` your handler sets itself must name only headers ocache varies on.** Setting `Vary: Accept-Language` on the response is the spec-correct way to say "this response is not interchangeable", but ocache keys on `varies` (and `Cookie` under `allowCookies`) and nothing else — so a response declaring a header that isn't in that list is **not stored**, and gets no synthesized `Cache-Control` either. Otherwise the first language rendered would be replayed to every other one, with that same `Vary` attached for downstream caches to trust. List the header in `varies` and the response caches normally:
>
> ```ts
> defineCachedHandler(
>   (event) =>
>     new Response(renderPage(event.req.headers.get("accept-language")), {
>       headers: { vary: "Accept-Language" }, // ocache merges/dedups its own copy in
>     }),
>   { maxAge: 300, varies: ["accept-language"] }, // ...and keys on it, so this caches
> );
> ```

> [!TIP]
> **Varying headers stay visible to the handler.** Their value is part of the cache key, so rendering from them is safe — each distinct value gets its own entry. This holds for the credential headers too: listing `cookie` or `authorization` in `varies` is a coarse opt-in that keys on _and_ forwards the raw header. They are only stripped when you _haven't_ listed them — see [Cookies](/guide/cookies) and the note below.

## Credential headers

`Authorization` and `Proxy-Authorization` **do not participate in caching by default**. On cacheable (`GET`/`HEAD`) requests both are stripped before the handler runs, exactly like a cookie outside [`allowCookies`](/guide/cookies) — so a handler can't render per-user content from a credential that isn't in the cache key and have it stored under the shared, anonymous key.

If your handler needs the credential, opt in with `allowAuthorization`:

```ts
const handler = defineCachedHandler(
  async (event) => {
    const token = event.req.headers.get("authorization");
    return Response.json(await loadDashboard(token));
  },
  {
    maxAge: 60,
    allowAuthorization: true, // keyed per credential, advertised in `Vary`, visible to the handler
  },
);
```

Opting in folds both header names into `varies`: they vary the cache key, they are merged into the response `Vary` header, and they reach the handler. (Listing `authorization` in `varies` yourself does the same thing.)

> [!CAUTION]
> **`allowAuthorization` caches one entry per credential value, shared by everyone presenting it.** Concurrent requests with the same token are coalesced into a single handler call, and the stored response is replayed to later ones. Only opt in when that is genuinely correct — a token that maps to more than one user's view, or one that rotates, still needs a user-specific `getKey`.
>
> When the response is per-user and shouldn't be shared at all, skip the cache for those requests instead:
>
> ```ts
> defineCachedHandler(myHandler, {
>   maxAge: 60,
>   shouldBypassCache: (event) => event.req.headers.has("authorization"),
> });
> ```

Only cacheable requests are affected: `POST` and friends — and anything your own `shouldBypassCache` excludes — bypass the cache and reach the handler with their credentials intact.

## Conditional requests & 304

When a client re-requests with `if-none-match` (matching the stored `etag`) or `if-modified-since` (at or after `last-modified`), the handler returns `304 Not Modified` with an empty body:

```ts
const handler = defineCachedHandler(() => new Response("<h1>Hi</h1>"), {
  maxAge: 300,
});

const first = await handler({ req: new Request(url) });
const etag = first.headers.get("etag");

// Browser revalidates with the etag it received
const second = await handler({
  req: new Request(url, { headers: { "if-none-match": etag } }),
});
second.status; // 304
```

The `304` echoes the `Vary` header so downstream caches keep the variant dimension.

## Headers-only mode

Set `headersOnly: true` to answer conditional requests **without** caching the response body. On a conditional match the handler short-circuits with a `304`; otherwise your handler runs and its response is returned as-is (never stored):

```ts
const handler = defineCachedHandler(myHandler, {
  headersOnly: true,
  maxAge: 60,
});
```

Use this when the handler already produces its own `etag`/`last-modified` and you only want the `304` shortcut, not full response storage.

## Cache-status header

By default a CDN-style `X-Cache` header is added, reporting how the response was served: `MISS`, `HIT`, `STALE`, or `REVALIDATED`.

```ts
defineCachedHandler(myHandler, { maxAge: 60 }); // adds X-Cache
defineCachedHandler(myHandler, { maxAge: 60, cacheStatusHeader: "x-my-cache" }); // custom name
defineCachedHandler(myHandler, { maxAge: 60, cacheStatusHeader: false }); // disable
```

## Framework integration hooks

To adapt to a specific framework's request/response types, override any of these:

- `toResponse(value, event)` — convert the handler's return value into a `Response`. Default: return it as-is if it's already a `Response`, otherwise `new Response(String(value))`.
- `createResponse(body, init)` — build the final `Response` served from the cache. `body` is a `string` (text), a `Uint8Array` (binary), or `null` (empty / `304`). Default: `new Response(body, init)`.
- `handleCacheHeaders(event, conditions)` — decide whether to answer with a `304`. Return `true` to short-circuit. Default: the built-in `if-none-match` / `if-modified-since` check.

```ts
const handler = defineCachedHandler(
  // Handler returns a plain object...
  async (event) => ({ id: 42, name: "Widget" }),
  {
    maxAge: 300,
    // ...toResponse turns it into JSON
    toResponse: (value) => Response.json(value),
  },
);
```

## On-demand revalidation

The returned handler carries `.expire(event)`, `.invalidate(event)`, and `.resolveKeys(event)`, mirroring the methods on a [cached function](/guide/invalidation). Each takes the request `event` and derives the exact key the handler cached it under:

```ts
await page.expire(event); // mark stale — serve stale once more, refresh in background (SWR)
await page.invalidate(event); // remove — next request blocks on a fresh render
```

They target the **resource**, not the method the event happens to carry: both the `GET` and the `HEAD` entry for that URL are purged (or expired) together, so nothing is left behind advertising the old `etag`. `.resolveKeys(event)` reports the same set — one key per `base` prefix per method variant, the event's own key first.

> [!NOTE]
> The standalone `invalidateCache()` / `expireCache()` helpers can't see the request method, so they only ever target the variant their arguments imply. Prefer the handler's own methods for cached handlers.

See [ISR → on-demand revalidation](/guide/isr#on-demand-revalidation) for the full recipe.
