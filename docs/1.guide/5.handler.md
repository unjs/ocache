# Caching HTTP Handlers

Wrap an HTTP handler with `defineCachedHandler` to cache its `Response` automatically. It supports `etag`, `last-modified`, and `304 Not Modified`. It works with any runtime that provides the standard `Request` and `Response` APIs. The event has the form `{ req: Request; url?: URL }`.

```ts
import { defineCachedHandler } from "ocache";

const handler = defineCachedHandler(
  async (event) => {
    const url = event.url ?? new URL(event.req.url);
    const product = await db.getProduct(url.pathname.split("/").pop());
    return Response.json(product);
  },
  {
    maxAge: 300, // cache fresh for 5 minutes
    swr: true, // serve stale while revalidating in the background
    staleMaxAge: 600, // ...for up to 10 minutes past expiry
  },
);

// Call it with any { req, url? } event
const res = await handler({ req: new Request("https://example.com/p/42") });
```

The first request runs your handler and stores the response. Later requests use the cache until the entry expires.

> [!NOTE]
> `maxAge` defaults to `1` second. Set it explicitly for anything you actually want cached.

## What it does

- **Cache keys** — ocache creates keys from the handler [name](#cache-key-name), request [origin](#multi-host-deployments), URL path, and request method. The keys also include query parameters and headers that you choose to vary.
- **Conditional requests** — ocache responds with `304 Not Modified` when the client sends a matching `if-none-match` or `if-modified-since`.
- **Response headers** — ocache creates `etag`, `last-modified`, and `cache-control` when the handler does not set them.
- **`Vary`** — ocache advertises the request headers that vary the response. These come from `varies` and include `Cookie` when you set `allowCookies`. ocache refuses to store a response if its own `Vary` names another header.
- **Binary responses** — ocache caches images, tiles, and other non-text bodies. It replays them byte for byte.
- **Resolution deadline** — a handler or upstream that never responds cannot block its cache key forever. ocache abandons the shared resolution after [`maxResolveTime`](/guide/functions#resolution-deadline), which is 30 seconds by default. Waiting requests reject instead of continuing to wait.

## Cacheable requests

ocache caches only `GET` and `HEAD` requests. All other methods, such as `POST`, `PUT`, and `DELETE`, bypass the cache and reach the handler unchanged.

A request with a `Range` header also bypasses the cache, for any method. A range request asks for a _part_ of a resource. Its response is valid only for the request that specified that range. If ocache stored it under a key without the range, all callers could receive one caller's partial response. It would also buffer a partial body without benefit. Your handler processes range requests without changes from ocache.

```ts
const handler = defineCachedHandler(myHandler, { maxAge: 60 });

await handler({ req: new Request(url) }); // GET  → cached
await handler({ req: new Request(url, { method: "POST", body }) }); // POST → runs the handler, body intact
```

> [!IMPORTANT]
> A bypassed response passes through exactly as the handler returned it. ocache does not buffer the body, so streaming bodies continue to work. It does not create cache headers or an incorrect `304`.

ocache caches `GET` and `HEAD` **separately**. A `HEAD` response is a different representation because a compliant framework removes its body. If both methods shared one entry, a `HEAD` request could store a response without a body. Later `GET` requests would then receive that empty response. Each method requires its own handler call for each resource and TTL. This prevents blank pages.

> [!NOTE]
> The method remains part of the key when you provide a custom `getKey`. Your key identifies _which content_ to cache. ocache adds the `GET` and `HEAD` separation. `GET` keys have no method component, so they do not change.

Use `shouldBypassCache` to bypass more requests. ocache combines it with the built-in checks using OR. It can only bypass _more_ requests. It cannot force ocache to cache another method or a range request:

```ts
const handler = defineCachedHandler(myHandler, {
  maxAge: 60,
  // Skip the cache for logged-in users
  shouldBypassCache: (event) => event.req.headers.has("authorization"),
});
```

A request excluded this way behaves like a `POST`. It reaches the handler **unchanged**, including its `Authorization` header, cookies, and full query string. Therefore, `shouldBypassCache` is an alternative to [`allowAuthorization`](#credential-headers). The handler can read the credential because ocache never stores or shares the response.

## Cache key name

Every key contains a `name`. ocache resolves it in the same way as the name of a [cached function](/guide/functions#cache-keys): `opts.name || handler.name || anon_<hash(handler)>`. The name prevents two handlers from colliding when they share one `storage` and use the same path.

```ts
const storage = createMemoryStorage();

// Named handlers → "/cache:handlers:dashboard:..." and "/cache:handlers:profile:..."
const dashboard = defineCachedHandler(
  async function dashboard(event) {
    return renderDashboard(event);
  },
  { maxAge: 60, storage },
);
const profile = defineCachedHandler(
  async function profile(event) {
    return renderProfile(event);
  },
  { maxAge: 60, storage },
);
```

> [!IMPORTANT]
> The fallback hashes the handler **source**. Handlers from the same factory have identical source but can have different closed-over variables. These handlers share a name. If they also share `storage`, they share entries. One tenant can then receive another tenant's cached response. Pass an explicit `name` or `getKey` when you build handlers in a loop or factory.
>
> ```ts
> // ✗ both handlers key identically
> const make = (tenant) => defineCachedHandler(() => render(tenant), { maxAge: 60, storage });
> // ✓ named per instance
> const make = (tenant) =>
>   defineCachedHandler(() => render(tenant), { maxAge: 60, name: `page-${tenant}`, storage });
> ```

ocache derives the name from the handler. The source hash stays stable across restarts, so you can use the keys with a persistent backend.

## Multi-host deployments

The request **origin** is part of the automatically generated key. The origin includes the scheme, host, and port. Therefore, one handler that serves several hostnames stores a separate entry for each host. This is common in a virtual host setup. `https://a.example/home` and `https://b.example/home` never share a cached rendering. Different schemes or ports also use separate entries.

The origin comes from `event.url`, or from `new URL(event.req.url)` when `event.url` is not available. It is the value that your adapter resolved, not the raw `Host` request header. Some adapters build the URL _from_ `Host`, so these values match. A reverse proxy before your app must still be trusted to normalize `Host` and `X-Forwarded-Host`.

> [!NOTE]
> A custom [`getKey`](/guide/query-params#edge-cases) replaces the full automatic key, including the origin. If your handler renders host-dependent content, add the origin to your key. Examples include canonical links, absolute asset URLs, and `Location`.

## Varying by request headers

By default, the cache key depends only on the request origin and URL path. All clients on the same host share one cached entry. List header names in `varies` to cache a separate variant for each header value:

```ts
const handler = defineCachedHandler(
  async (event) => {
    const lang = event.req.headers.get("accept-language") ?? "en";
    return new Response(renderPage(lang), {
      headers: { "content-type": "text/html" },
    });
  },
  {
    maxAge: 300,
    varies: ["accept-language"], // one cached entry per language
  },
);
```

ocache also adds these header names to the response `Vary` header. It removes duplicates without regard to case. It does not change a `Vary: *` set by the handler. As a result, downstream caches and CDNs also store each variant separately. [`allowCookies`](/guide/cookies) also adds `Cookie` to `Vary`. The cache key uses only the allowed cookie subset, but the response still varies by the full header because `Vary` cannot describe a subset. [`allowQuery`](/guide/query-params) adds nothing to `Vary`. Query parameters are in the URL, and downstream caches already include the URL in their keys.

> [!IMPORTANT]
> **A `Vary` set by your handler must name only headers that ocache varies on.** `Vary: Accept-Language` correctly states that responses for different languages are not interchangeable. However, ocache keys only on `varies` and on `Cookie` when you set `allowCookies`. It **does not store** a response that names another header. It also does not synthesize `Cache-Control` for that response. Otherwise, ocache could replay the first language to all other languages. The response would still contain `Vary`, which downstream caches would trust. Add the header to `varies` to cache the response correctly:
>
> ```ts
> defineCachedHandler(
>   (event) =>
>     new Response(renderPage(event.req.headers.get("accept-language")), {
>       headers: { vary: "Accept-Language" }, // ocache merges/dedups its own copy in
>     }),
>   { maxAge: 300, varies: ["accept-language"] }, // ...and keys on it, so this caches
> );
> ```

> [!TIP]
> **The handler can read varying headers.** Their values are part of the cache key, so each distinct value gets its own entry. It is safe to render content from them. This also applies to credential headers. Listing `cookie` or `authorization` in `varies` is a broad opt-in. ocache keys on the raw header and forwards it to the handler. ocache removes these headers only when you do _not_ list them. See [Cookies](/guide/cookies) and the next section.

## Headers the handler can't see

**For cacheable requests, a handler can read only the headers that the cache key covers.** ocache removes all other request headers before it runs the handler. For a removed header, `event.req.headers.get(...)` returns `null`.

```ts
defineCachedHandler(
  (event) => {
    const tenant = event.req.headers.get("x-api-key"); // null — not in `varies`
    return Response.json(loadTenant(tenant));
  },
  { maxAge: 300 },
);
```

This prevents a handler from rendering content from an input that the key does not distinguish. Without this rule, ocache could store the first caller's tenant page under a shared key. It could advertise the page to browsers and CDNs with a synthesized `max-age` and no `Vary`. It could then replay the page to everyone else for the rest of the TTL. The same risk applies to `Accept`, `Accept-Language`, and `Origin` when it is copied into a CORS header. It also applies to `X-Forwarded-Host` and `X-Forwarded-Proto`. Behind a proxy, the host in the cache key can be the internal host. If a forwarded host reached the handler, both tenants could use one entry.

You can use either of these fixes:

- **`varies: ["x-api-key"]`** — the header becomes part of the entry key and reaches the handler. ocache also advertises it in the response `Vary`. Each distinct value gets one entry.
- **[`shouldBypassCache`](#cacheable-requests)** — keep these requests out of the cache. A bypassed request reaches the handler unchanged.

ocache does not remove a small set of headers because a cache key cannot usefully cover them. These are `Host`, which the URL authority already covers; `If-None-Match` and `If-Modified-Since`, which ocache uses for [`304`](#conditional-requests--304); and the trace headers `traceparent`, `tracestate`, `X-Request-Id`, and `X-Correlation-Id`. `User-Agent` is **not** exempt. Output for different devices or bots needs separate keys. Add `User-Agent` to `varies` if you render from it.

> [!NOTE]
> ocache narrows only cacheable (`GET` and `HEAD`) requests. It narrows only the request that the handler receives. Your middleware, framework, and runtime still receive the original request.

## Credential headers

This rule is especially important for `Authorization` and `Proxy-Authorization`. These headers **do not participate in caching by default**. For cacheable (`GET` and `HEAD`) requests, ocache removes both headers before the handler runs. It treats them like a cookie that is not in [`allowCookies`](/guide/cookies). Therefore, a handler cannot render per-user content from a credential that is missing from the cache key. This prevents storage under a shared anonymous key.

If your handler needs the credential, opt in with `allowAuthorization`:

```ts
const handler = defineCachedHandler(
  async (event) => {
    const token = event.req.headers.get("authorization");
    return Response.json(await loadDashboard(token));
  },
  {
    maxAge: 60,
    allowAuthorization: true, // keyed per credential, advertised in `Vary`, visible to the handler
  },
);
```

This opt-in adds both header names to `varies`. They vary the cache key and reach the handler. ocache also adds them to the response `Vary` header. Listing `authorization` in `varies` has the same effect.

> [!CAUTION]
> **`allowAuthorization` caches one entry for each credential value. All clients that send that value share the entry.** ocache combines concurrent requests with the same token into one handler call. It replays the stored response to later requests. Use this option only when this behavior is correct. A token that maps to more than one user view still needs a user-specific `getKey`. A token that rotates also needs one.
>
> When the response is per-user and shouldn't be shared at all, skip the cache for those requests instead:
>
> ```ts
> defineCachedHandler(myHandler, {
>   maxAge: 60,
>   shouldBypassCache: (event) => event.req.headers.has("authorization"),
> });
> ```

This affects only cacheable requests. Other methods, such as `POST`, bypass the cache. Requests excluded by `shouldBypassCache` also bypass it. These requests reach the handler with their credentials unchanged.

## Conditional requests & 304

The handler returns `304 Not Modified` with an empty body when `if-none-match` matches the stored `etag`. It also returns 304 when `if-modified-since` is at or after `last-modified`:

```ts
const handler = defineCachedHandler(() => new Response("<h1>Hi</h1>"), {
  maxAge: 300,
});

const first = await handler({ req: new Request(url) });
const etag = first.headers.get("etag");

// Browser revalidates with the etag it received
const second = await handler({
  req: new Request(url, { headers: { "if-none-match": etag } }),
});
second.status; // 304
```

The `304` repeats the `Vary` header. This lets downstream caches keep the variant dimension.

## Headers-only mode

Set `headersOnly: true` to answer conditional requests **without** caching the response body. When a condition matches, the handler immediately returns a `304`. Otherwise, your handler runs and ocache returns its response unchanged. It never stores the response:

```ts
const handler = defineCachedHandler(myHandler, {
  headersOnly: true,
  maxAge: 60,
});
```

Use this option when the handler already creates its own `etag` and `last-modified`. It gives you the `304` shortcut without full response storage.

## Cache-status header

By default, ocache adds a CDN-style `X-Cache` header. It reports how ocache served the response: `MISS`, `HIT`, `STALE`, or `REVALIDATED`.

```ts
defineCachedHandler(myHandler, { maxAge: 60 }); // adds X-Cache
defineCachedHandler(myHandler, { maxAge: 60, cacheStatusHeader: "x-my-cache" }); // custom name
defineCachedHandler(myHandler, { maxAge: 60, cacheStatusHeader: false }); // disable
```

## Cache tags

Set `tags` to advertise a `Cache-Tag` response header. A downstream cache that supports tag-based purging, such as [Cloudflare Workers Cache](https://blog.cloudflare.com/workers-cache/), indexes the tags and can then purge every response that carries one:

```ts
const handler = defineCachedHandler(renderProduct, {
  maxAge: 60,
  tags: ["products", "product:123"], // → Cache-Tag: products, product:123
});
```

ocache trims and removes duplicate tags, then joins them with `", "`. An omitted, empty, or whitespace-only list emits no header. ocache never changes a `Cache-Tag` header that the handler sets.

> [!IMPORTANT]
> This header is **advisory**. ocache does not index or purge its own storage by tag. Use [`.expire()` / `.invalidate()`](#on-demand-revalidation) for ocache's storage and your CDN's own purge API for its copy.

## Framework integration hooks

Override any of these hooks to support the request and response types of a specific framework:

- `toResponse(value, event)` — converts the handler return value to a `Response`. By default, it returns an existing `Response` unchanged. For other values, it returns `new Response(String(value))`.
- `createResponse(body, init)` — builds the final `Response` served from the cache. `body` is a `string` for text, a `Uint8Array` for binary data, or `null` for an empty response or `304`. The default is `new Response(body, init)`.
- `handleCacheHeaders(event, conditions)` — decides whether to respond with a `304`. Return `true` to respond immediately. The default uses the built-in `if-none-match` and `if-modified-since` check.

```ts
const handler = defineCachedHandler(
  // Handler returns a plain object...
  async (event) => ({ id: 42, name: "Widget" }),
  {
    maxAge: 300,
    // ...toResponse turns it into JSON
    toResponse: (value) => Response.json(value),
  },
);
```

## On-demand revalidation

The returned handler provides `.expire(event)`, `.invalidate(event)`, and `.resolveKeys(event)`. These methods match the methods on a [cached function](/guide/invalidation). Each method takes a request `event` and gets the exact key that the handler used:

```ts
await page.expire(event); // mark stale — serve stale once more, refresh in background (SWR)
await page.invalidate(event); // remove — next request blocks on a fresh render
```

These methods target the **resource**, not only the method in the event. They purge or expire both the `GET` and `HEAD` entries for that URL. No entry remains that advertises the old `etag`. `.resolveKeys(event)` returns the same set. It returns one key for each `base` prefix and method variant, with the event key first.

> [!NOTE]
> The standalone `invalidateCache()` and `expireCache()` helpers cannot see the request method. They target only the variant implied by their arguments. For cached handlers, use the handler methods when possible.

See [ISR → on-demand revalidation](/guide/isr#on-demand-revalidation) for the full recipe.
