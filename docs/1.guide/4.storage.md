# Storage

Every cached function and handler owns its storage. By default that's a **fresh in-memory `Map` per instance**, but you can hand any instance a backend that implements the minimal `StorageInterface` — and share one between as many cached functions as you like.

There is no global storage. Two cached functions that both take the default never see each other's entries, even under an identical name and key, so two independent libraries or apps in the same process cannot collide by accident. Sharing a cache is always explicit: pass the _same_ `storage` to everyone who should see it.

## The Storage Interface

A storage only needs two methods, `get` and `set`. Both may be synchronous or return a promise:

```ts
interface StorageInterface {
  get<T = unknown>(key: string): T | null | Promise<T | null>;
  set<T = unknown>(key: string, value: T, opts?: { ttl?: number }): void | Promise<void>;
}
```

- `get(key)` returns the stored value, or `null` when the key is missing.
- `set(key, value, opts)` stores a value. `opts.ttl` is a lifetime in **seconds** (optional).
- Setting a **nullish** value (`null` or `undefined`) via `set` **deletes** the entry. This is how invalidation reaches your backend, so make sure your `set` handles it.

## Custom Storage

Pass your backend as the `storage` option. Here it is backed by Redis:

```ts
import { defineCachedFunction } from "ocache";
import type { StorageInterface } from "ocache";

const redisStorage: StorageInterface = {
  async get(key) {
    const raw = await redis.get(key);
    return raw === null ? null : JSON.parse(raw);
  },
  async set(key, value, opts) {
    // A nullish value means "delete this entry" (used by invalidation).
    if (value === null || value === undefined) {
      await redis.del(key);
      return;
    }
    // opts.ttl is in seconds — Redis' EX option expects seconds too.
    await redis.set(key, JSON.stringify(value), opts?.ttl ? { EX: opts.ttl } : undefined);
  },
};

const getUser = defineCachedFunction(fetchUser, { maxAge: 60, storage: redisStorage });
```

Because the interface is so small, [unstorage](https://unstorage.unjs.io) drivers (filesystem, Cloudflare KV, S3, Redis, and many more) drop in with a thin adapter:

```ts
import { createStorage } from "unstorage";
import redisDriver from "unstorage/drivers/redis";

const unstorage = createStorage({ driver: redisDriver({/* ... */}) });

const storage: StorageInterface = {
  get: (key) => unstorage.getItem(key),
  set: (key, value, opts) =>
    value === null || value === undefined
      ? unstorage.removeItem(key)
      : unstorage.setItem(key, value, { ttl: opts?.ttl }),
};
```

## Sharing a Storage

Pass the same `storage` to every cached function or handler that should share a cache:

```ts
const storage = createMemoryStorage();

const getUser = defineCachedFunction(fetchUser, { maxAge: 60, storage });
const getPosts = defineCachedFunction(fetchPosts, { maxAge: 60, storage });
```

They still key entries by `base`/`group`/`name`, so sharing a backend does not mean sharing entries — it means sharing one connection, one eviction budget, and one place to purge.

> [!IMPORTANT]
> The `name` is what separates them, and it defaults to the function's or [handler's](/guide/handler#cache-key-name) own name, falling back to a hash of its source. Instances built by a factory or a loop have identical source, so they resolve to the **same** name — on a shared storage they then share entries. Give those an explicit `name`.

## Late Binding

Handlers are usually defined at module load, while the real backend only exists once the server has started. Pass a **factory** instead of an instance: it is called on the first actual cache read or write — never at definition time — and at most once per cached function or handler.

```ts
let storage: StorageInterface;

const handler = defineCachedHandler(renderPage, {
  maxAge: 60,
  storage: () => storage, // resolved on first use, once
});

// ...later, at server start
storage = redisStorage;
```

> [!NOTE]
> The resolved storage is memoized back onto the options object you passed. That is what lets the standalone `invalidateCache()` / `expireCache()` helpers reach the same store — hand them the _same_ options object you cached with. A different object literal, even a structurally identical one, resolves its own storage and silently purges nothing. See [Invalidation & Expiration](/guide/invalidation).

## Memory Storage & LRU

The default storage — a fresh one per cached function/handler — is created with `createMemoryStorage`. It holds at most **10 000 entries** _and_ at most **100 MB**, evicting the least-recently-used entries once either ceiling is exceeded (LRU). Reading or writing a key marks it as most-recently-used.

Both ceilings apply, and they bound different things: `maxSize` bounds the entry **count**, `maxBytes` bounds the **memory**. `maxSize` on its own is not a memory bound — retained bytes are `maxSize × whatever an entry weighs`, and for cached HTTP responses that weight is decided by the pages you serve (10 000 × 1 MB is 10 GB, and an out-of-memory kill is not something your process can catch). Set either to `Infinity` (or `0`) to disable it:

```ts
import { createMemoryStorage } from "ocache";

// Change the ceilings.
const storage = createMemoryStorage({
  maxSize: 50_000,
  maxBytes: 512 * 1024 * 1024,
});

// Opt out of the entry ceiling, keep the byte budget.
const bigCache = createMemoryStorage({ maxSize: Number.POSITIVE_INFINITY });

const cached = defineCachedFunction(fn, { maxAge: 60, storage });
```

The byte figure is an **estimate**: strings (which is what a cached response body is) are charged at 2 bytes per character — the upper bound an engine may retain — plus the key's own bytes and a small per-entry overhead. Over-charging is deliberate; a budget that under-counts is not a bound. Pass `sizeOf` to replace the estimate with your own, which then owns the whole per-entry charge:

```ts
const storage = createMemoryStorage({
  maxBytes: 64 * 1024 * 1024,
  sizeOf: (value, key) => key.length + JSON.stringify(value).length,
});
```

> [!NOTE]
> An entry that alone exceeds `maxBytes` is **not stored** (and any previous value under its key is dropped) — evicting the rest of the cache for something that still would not fit would let one oversized response flush everything else. Raise `maxBytes` if you cache a few very large values.

> [!NOTE]
> `maxBytes` bounds what the cache **retains**, which is not the same as what a single value costs to **produce**: by the time storage is offered an entry, the memory to build it has already been spent. For cached HTTP handlers that other bound is [`maxBodySize`](/guide/handler#large-responses) — a response body over it (5 MB by default) is streamed through to the caller and never buffered at all.

Memory storage also honors the per-entry TTL: expired entries return `null` and are cleaned up automatically.

## Multi-tier Caching

The `base` option prefixes cache keys. Pass an **array** of prefixes to enable multi-tier caching:

- **On read**, each prefix is tried in order and the first hit wins.
- **On write**, the entry is stored under _every_ prefix.

```ts
import { defineCachedFunction } from "ocache";

const cachedFetch = defineCachedFunction(
  async (url: string) => {
    const res = await fetch(url);
    return res.json();
  },
  {
    maxAge: 60,
    base: ["/local", "/remote"], // read "/local" first, then "/remote"; write both
  },
);
```

This suits layered setups (e.g. a fast local tier in front of a shared remote tier): reads prefer the nearest tier while every tier stays populated on writes. A single string (the default is `"/cache"`) keeps everything in one tier.

Invalidation and expiration operate across all tiers — see [Invalidation & Expiration](/guide/invalidation).
