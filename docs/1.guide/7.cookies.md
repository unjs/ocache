# Cookies

**By default, no cookies take part in caching — in either direction.** This is a secure default:

- The `Cookie` request header is stripped before your handler runs, so the handler can't produce cookie-specific output that then gets cached and served to someone else.
- Cookies never vary the cache key.
- Any `Set-Cookie` your handler sets is removed before the response is cached or returned.

Together these keep a per-request cookie (such as a session id) from ever reaching another visitor — whether through a later cache hit or a concurrent request that is served the same cached response.

The request side can be opened back up — per cookie with [`allowCookies`](#allowing-specific-cookies), or wholesale with [`varies: ["cookie"]`](#varying-by-the-whole-cookie-header). **The response side cannot:** no `Set-Cookie` ever survives a cacheable response. See [Setting cookies](#setting-cookies).

```ts
const page = defineCachedHandler(
  async (event) => {
    event.req.headers.get("cookie"); // always null for cached GET/HEAD requests
    return new Response(await renderPage(), {
      headers: { "content-type": "text/html" },
    });
  },
  { maxAge: 60 },
);
```

> [!NOTE]
> This only applies to cacheable requests (`GET` / `HEAD`). Methods that bypass the cache entirely (`POST`, `PUT`, …) reach the handler with the request untouched — cookies, headers, query, and body included — and their `Set-Cookie` is passed straight through.

## Allowing specific cookies

Set `allowCookies` to an allowlist of cookie names to opt specific **incoming** cookies back in. For those cookies only:

- they stay in the `Cookie` header your handler sees,
- they vary the cache key (sorted and order-independent, like [`allowQuery`](/guide/query-params), so only that subset is part of the key — not the entire raw `Cookie` header).

Every other cookie is still stripped from the request, and the rest of the response is cached as usual.

```ts
const page = defineCachedHandler(myHandler, {
  maxAge: 300,
  allowCookies: ["theme"], // theme=dark and theme=light cache separately; every other cookie is ignored
});
```

Cookie names are **case-sensitive**. `allowCookies` supersedes `varies: ["cookie"]` — set the allowlist and drop the coarse `varies` entry (the `Vary: Cookie` below is emitted either way). With both set, the allowlist wins in both directions: the key carries the subset, and the handler sees the filtered header rather than the raw one.

Allowlist a cookie whose value legitimately selects a _representation_ — a `theme` or `locale` preference that becomes part of the cache key — not a per-user secret. Everyone presenting the same value is served one shared entry.

## Varying by the whole `Cookie` header

Listing `cookie` in [`varies`](/guide/handler#varying-by-request-headers) without an allowlist is the coarse form of the same opt-in — exactly like listing `authorization` there instead of setting [`allowAuthorization`](/guide/handler#credential-headers). The **raw** `Cookie` header then:

- composes the cache key (the whole header value, verbatim),
- is forwarded to your handler untouched,
- is advertised as `Vary: Cookie`.

```ts
const page = defineCachedHandler(
  (event) => renderFor(event.req.headers.get("cookie")), // the full raw header
  { maxAge: 60, varies: ["cookie"] },
);
```

> [!WARNING]
> **You own the fragmentation.** One entry per distinct `Cookie` header value means, in practice, one entry per visitor: any analytics, consent or A/B cookie makes a request its own variant, so the cache stops collapsing anything. `allowCookies` exists to key on the handful of names that actually select a representation — prefer it, and reach for `varies: ["cookie"]` only when the handler genuinely needs the whole header.

### `allowCookies` emits `Vary: Cookie`

Setting `allowCookies` adds `Cookie` to the response's [`Vary`](/guide/handler#varying-by-request-headers) header. ocache keys on a hash of the allowlisted subset, but `Vary` has no finer granularity than the header name — there is no way to tell a CDN "only the `theme` cookie matters here".

```http
Cache-Control: max-age=300, s-maxage=300
Vary: Cookie
```

This is the truth about the response, and it has a price:

> [!WARNING]
> **`Vary: Cookie` is destructive to CDN and shared-proxy hit rates.** Almost every visitor carries _some_ cookie — analytics, A/B, consent — and each distinct `Cookie` header is a separate variant downstream, so shared caching effectively stops. Your ocache entries are unaffected (they key on the allowlisted subset only); it is the cache _in front_ of you that stops collapsing requests.

Until ocache v1 this header was omitted, so a cookie-keyed route advertised `s-maxage` with no `Vary` at all — CDNs cached it happily and served **one visitor's variant to everyone**. If your downstream hit rate drops after upgrading, this is why, and the previous behavior was serving wrong content to get it.

If downstream hit rate is what you need, **don't key by cookie**:

- Select the representation from the URL instead — a `?theme=dark` param ([`allowQuery`](/guide/query-params)) or a distinct path. Those vary the key without touching `Vary`, so a CDN can cache each variant.
- Or keep the cookie-keyed cache server-side only and advertise nothing downstream with [`sendCacheControl: false`](/guide/cache-control).

## Setting cookies

**`allowCookies` has no effect on the response: no `Set-Cookie` ever survives a cacheable (`GET`/`HEAD`) route.** It is removed both from the stored entry and from the response the caller receives — including the caller whose request produced it.

This is not a conservative default you can opt out of, and it is deliberate. A cached response is a shared object: it is replayed to every later request that hits the same key, and to concurrent callers coalesced onto a single handler call. A cookie minted inside it therefore reaches people it was never minted for. Allowing a name through would only move that leak one opt-in away:

```ts
// Even with allowCookies: ["sid"], the Set-Cookie below never reaches any caller.
const page = defineCachedHandler(
  () => new Response("hello", { headers: { "set-cookie": `sid=${newSessionId()}` } }),
  { maxAge: 60, allowCookies: ["sid"] },
);
// First visitor:  MISS, no Set-Cookie.
// Second visitor: HIT (same key — neither had a `sid`), no Set-Cookie.
// Previously both received `sid=<the first visitor's id>` — a session-fixation hole.
```

To mint a per-request cookie, serve it from a request that bypasses the cache. Only `GET` and `HEAD` are cacheable, so a `POST` (or any request excluded by your own `shouldBypassCache`) reaches the handler untouched and returns its `Set-Cookie` unchanged:

```ts
const login = defineCachedHandler(
  async (event) => {
    if (event.req.method === "POST") {
      // Bypassed: this Set-Cookie is neither stored nor shared.
      return new Response("ok", {
        headers: { "set-cookie": `sid=${await startSession(event)}; HttpOnly; Path=/` },
      });
    }
    return new Response(await renderLoginPage());
  },
  { maxAge: 60 },
);
```

## Caveats

- **Custom `getKey`.** As with `allowQuery`, a custom `getKey` controls the cache key entirely, so allowlisted cookies no longer vary it automatically. If your handler's output depends on a cookie, incorporate it into `getKey` yourself. (The handler-visible `Cookie` header is still filtered to the allowlist regardless.)
- **Entries written by older versions.** A stored response that carries a `Set-Cookie` — cached by an ocache version that still kept allowlisted cookies — is refused rather than served, so upgrading can't replay one that is already in your storage.
